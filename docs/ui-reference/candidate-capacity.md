# 候補の一覧・横比較・検査領域の収容量

2026-10-15。独立担当による構造レビュー。既存領域を完成済みとせず、候補の集合を選ぶ→同じ相手で比較する→1展開を検査する仕事を辿った。

## 初巡から派生した枝

- 一覧で比較チェックを入れる→横比較は一覧とInspector全体の後にあり、Inspectorの内容量に押される。左に一覧＋横比較、右に選択候補Inspectorを置いた。同時に必要な情報なので排他的タブにはしない。
- 比較を追加した後→一覧の候補が多いと横比較まで届かない。比較中だけ一覧を25vh（150–260px）に抑える。一覧は消さず、チェック追加・解除と行選択を続けられる。
- 横比較を見る→候補が増え横方向に移動すると相手を忘れる。比較表の相手列と候補見出しを固定した。表外の説明や対象を増やす代わりに実データの識別を保つ。
- 一覧を上下する→列名が消える。列見出しを固定した。行のフォーカス・選択・比較チェックの意味は既存契約を保つ。
- 選択展開の表示→ResponseBrowserが「共通比較」と「共通比較待ち」を区別するようになった後も、旧shared単独の補足が残る。重複補足を除いた。
- 狭幅→680px以下で一覧・比較を同じ列のままInspectorを下へ配置。全体横溢れを起こさず、各表内のスクロールを維持する。Inspectorに行くには下方向移動が必要。この制約を隠すために比較表を折り畳むことはしていない。

## 配置根拠

添付PDF `professional_high_density_ui_patterns.pdf` のp.13（04 Split view）を画像化して確認した。関連情報の同時表示と独立したスクロールを採用。汎用ドッキング基盤や新しいレイアウト保存UIはこの枝には導入しない。外側の既存エディタ分割と最大化があるため、候補内で同じ仕組みを重複実装するとフォーカスと復元の契約が増える。

Godot `4.5-stable` の [inspector_dock.cpp](https://github.com/godotengine/godot/blob/4.5-stable/editor/docks/inspector_dock.cpp) を取得し、`InspectorDock` のInspector生成・`SIZE_EXPAND_FILL`・`register_text_enter`を再確認。[公式Inspector資料](https://docs.godotengine.org/en/stable/tutorials/editor/inspector_dock.html)の選択変更に追随する内容と照合。独立した側面検査領域を使い、選択対象に属する操作をそこで完結する関係を採用。Godot実機は操作していない。計算結果を任意編集プロパティに変える構造は採用しない。

## 実操作と再訪

別のheadless Chromeで、このチェックアウトの `http://127.0.0.1:5187` に接続。174秒の検証局面から新規探索し、実エンジンが返した5候補のうち3候補を比較へ追加した。fixtureの注入なし。

- 1280×720（候補パネル863px）で一覧y219.5/高さ180、横比較y407.5、Inspector y219.5/高さ540。横比較の開始がInspector最下部に依存しない。
- 一覧行をフォーカスして下矢印を押し、選択行とInspectorの対象更新を確認。
- 比較セルを選び、最小点差と2番目の裁定展開の選択・3D/A/B操作が表示されることを確認。
- 700×900で候補領域668px、scrollWidth668px。1列へ切り替わり領域全体の横溢れなし。
- 再読込後も「候補を並べて比較 · 3件」が復元された。
- `npm run typecheck`成功。

スクリーンショットは `/tmp/candidate-capacity-wide.png`、`/tmp/candidate-capacity-narrow.png`。修正前の専用計測はHMR更新と重なったため前後差の数値は主張しない。

次の枝は狭幅で比較表からInspectorへ移る距離と、非常に多数の候補に対する列幅・表示速度。今回の5候補だけで仮想化の必要性や性能効果は確定しない。既存最大化で検査領域を広げる手段はあるが、狭幅内の往復を完全に解消したとは扱わない。
