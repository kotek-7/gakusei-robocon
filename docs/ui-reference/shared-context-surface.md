# 表示中の試合の共通入口

対象は `shell/TopBar.tsx`、`ReplayContext.tsx`、`StatusBar.tsx`。ワークスペース切替後も、実際に表示中の経路の出典を確認し、その候補へ戻る操作を扱う。

## 配置根拠

既存の探索選択欄の隣を、表示中の試合への一つの入口にした。新しい帯や、探索・構成・候補・相手ごとのボタン列は増設しない。探索は切替対象、試合は確認と元候補への移動という異なる意味なので、それぞれネイティブselectと短いポップオーバー入口を使う。構成・候補ID・相手・局面は開いた時だけ表示する。A/Bは各比較領域の文脈なのでこの入口に加えない。

再生時刻は頻用の共通状態なので既存ステータスバーに残し、狭幅でも隠さない。進捗名自体が計算パネルへの入口になっているため、同じ操作の「計算詳細」ボタンは除いた。

一覧の選択と再生経路を区別する。Session.replayを現存候補に照合し、固定evidenceのnode/pathが表示中経路と一致した場合だけ候補を名乗る。出典のない経路は局面番号、失効した出典は局面番号と確認不能の説明にする。候補には一覧と同じ短縮IDを使い、別の番号体系を作らない。

## パターン資料

- ユーザー提供 `professional_high_density_ui_patterns.pdf` p21（16 Breadcrumbs）、p24（20 Reveal）、p35（36 Single source of selection truth）。p21の図をレンダーして確認。パスを短く保ち、展開時に対象詳細と移動を示す構成を採用。アプリの構成/候補/相手はディレクトリ階層ではないため、架空の多段パンくずや兄弟pickerは作らない。
- VS Code [Code Navigation](https://code.visualstudio.com/docs/editing/editingevolved)、公式Breadcrumbs画面とPDFの再構成図。固定タグ [1.96.4 breadcrumbsControl.ts](https://github.com/microsoft/vscode/blob/1.96.4/src/vs/workbench/browser/parts/editor/breadcrumbsControl.ts) の `_onSelectEvent`、`_revealInEditor`、`showContextView` を確認。選択と移動の分離、クリック時だけpicker、画面端で幅/位置を調整、キャンセル時の復元を参考とした。VS Codeアプリ自体は操作していない。

## 巡回

1. 実装と既存fixtureを確認。既存では一覧に候補選択がある一方、表示経路は初期局面N1だった。常設の候補名を一覧選択から導出しない契約を採用。単一入口・ポップオーバー・再生位置の常設を実装。
2. 1280px/390pxの実画面を確認。新しい常設行はなし。Escで入口にフォーカス復帰、document幅は390px。390pxでは既存CSSとの競合により探索selectが潰れたため最小幅80pxを指定。独立パターン担当のレビューを受け、狭幅でも「表示中」を残した。親レビューを受け、候補順序番号を廃して既存IDへ統一。元候補への移動を再生時刻不変の `strategy.reveal` に接続。

担当は本UI担当1名。パターン担当と親から独立レビューを受けた。追加子委譲なし。新たな常設ボタンやピン止めUIは、今回の仕事に必要な対象が増えないため不採用。キーボード・狭幅・出典整合と戻り操作が今回の終了条件。

確認結果: 実際の候補を3D表示して「条件」へ切替後も候補P-8a2252d049ec・相手対応4・局面N7を保持。390pxでも探索選択と「表示中」が見える。ポップオーバーの左端はみ出しを検出し、固定幅に対するright座標の上限を設けて修正。Escの起点フォーカス復帰と横幅390pxを再確認。`npm --prefix web run typecheck` 成功。3Dキャンバス自体は検証ブラウザのWebGL無効条件下なので、経路更新・共通表示・他エディタ操作を検証した。

統合時の見直しでは狭幅で選択物のラベルが消える点を確認した。非nodeの共通選択（ロボット・スポット・物体等）がある場合だけ同じポップオーバーの「選択」に載せた。既存ステータスバーと同じ識別ラベル関数を共有し、追加の常設表示を作らない。
