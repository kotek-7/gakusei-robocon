# 候補単体の追加探索操作

2026-10-15。担当 focused_controls。編集対象は StrategyExploration、explorationCommands、explorationIdentity と専用CSS。ブラウザーは統合担当が操作するため、ここでの巡回はソース・状態契約・型検査による。実画面を操作したと扱わない。

## 作業と配置

候補選択後、その候補だけに計算時間を使い、保存して停止し、増えた結果から展開へ移る。固定結果の閲覧とは仕事が違うため「追加探索」1ビュー内で実行条件、計算状況、同じ対象の実行履歴を扱う。

| 部品 | 対象と意味 | 採用理由・状態 |
|---|---|---|
| 計算select | 候補、計算内容の選択 | 相手探索と既知の相手の検査は排他的。切替自体は実行しない |
| 時間selectと実行 | 候補、計算制限と実行 | 時間を確認してから開始。他計算中、対象消失、範囲終了時は無効 |
| 保存して停止 | 実行中の候補と計算モード | targetをAPIへ渡し、別候補・別モードを誤停止しない |
| 状態行 | 実行対象、状態 | 候補変更中も実際に計算している構成・候補を表示 |
| 件数と最小点差 | 選択候補、結果 | 最小点差は検査済み集合内。結果から既存の展開選択へ接続 |
| 実行履歴 | 選択候補、保存された実行結果 | 開始時刻・時間・増加数・点差前後を列で読む。追加結果ありの絞込と段階表示 |
| ? | それぞれの計算・進捗の意味 | 長文を常設せず、限定探索と件数の意味を補足 |

## OSS・カタログ根拠

既存の `candidate-expansion-research.md` の Godot 4.5-stable調査を再利用。対象は `editor/docks/inspector_dock.cpp` の `_prepare_resource_extra_popup` と `_get_current_resource`、`editor/inspector/editor_inspector.cpp` の `EditorInspector::edit`。現在対象から操作対象を解決し、無効条件を一致させるという課題が同じ。見た目やGodot実機の挙動を新しく確認したとは扱わない。今回もコマンド実行時に現在の領域・候補を照合する。選択履歴や汎用プロパティエディターの全面移植はしない。

参考PDFの既存調査記録にある保存ビュー・文脈別操作の原則を使用。履歴の絞込は同じ候補の追加成果を探す用途に限定し、候補比較用の多条件検索を複製しない。

## 巡回

1. 既存の計算と進捗、詳細ビュー、useQuery、コマンド機構を確認。候補専用開始・保存停止・モード選択・待機列・対抗結果リンクを検討。空のメニュー基盤や比較用カードは不要と判断。
2. エンジン担当とtarget/API/履歴契約を合意。実行条件と停止を登録コマンドに接続し、予算10秒〜24時間を用意。実行対象と閲覧対象を区別する状態行を追加。
3. 候補切替中の進行をソース確認。古い対象の操作を防ぐ現在領域の候補ID検査を追加。展開だけの変更では実行対象が変わらない。2ケースのテストにまとめ、異なるsearch/run/candidate/nullを検査。
4. 終了時の読み直しを検討し、今回の追加展開・検査手順・最小点差前後の保存履歴を実装。フィルターと10件からの追加表示で履歴増加に対応。停止理由はruntimeのキーに合わせた日本語。query更新不足を発見し親へdata invalidation変更を依頼。
5. タブ移動による設定消失を検討。settings/onSettingsを追加し親の領域状態に保存。経過時間は実開始時刻から算出し、予測進捗率は作らない。共有エラー表示、キーボード利用可能な表スクロール、折返しを追加。

2件の対象同一性テスト成功、型検査成功（統合前）。UIの実操作・再読込確認は親の統合検証へ接続する。担当の再委譲は同時枠が全使用中のため未実施。未着手の独立枝は実行履歴から当時増えた展開集合への直接リンク（現契約は件数スナップショットのみ）、予算の任意数値入力。現在は最小点差の展開への直接リンクと固定予算が動作する。成果件数を勝率や網羅率へ変換しない。
