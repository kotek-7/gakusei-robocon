# 候補を指定する追加探索

担当: focused_engine。UI接続: focused_controls。下位担当: focused_tests（独立した隔離・保存・再開テスト）。

## 契約と範囲

`job.start` の `kind: discovery` に `target: { run, candidate, mode }` を追加。modeはcounter（赤固定・青探索）とcompare（既存の青手順を固定検査）。選択対象と構成番号を開始前に照合する。新たな赤候補の生成には計算を使わない。既存DJobの未探索分岐をそのまま再開する。

counterが新しい相手手順を発見した場合は従来通り共有辞書と将来の比較ジョブへ登録する。ただし対象外候補のジョブを進めず、対象外候補に実行結果を追加しない。pending数は共有辞書に従って変わる。global schedulerの進行位置はfocused実行では変えない。

`candidate.analysis`は対象候補のcounter/compareごとの試行数、未処理局面、既知の残り選択数、ジョブ数・終了状態、結果数、相手手順数、検査済み数、観測した最小点差、実行履歴を返す。残り選択数は展開済み局面で分かっている分のみであり、探索全量・進捗率ではない。

`Search.discovery.activeTarget`が実行対象を示す。`job.pause`にtargetを渡すと一致を照合し、候補切替後や別モード実行中の誤停止を防ぐ。従来の全体停止も残す。

## 反復記録

1. 既存scheduler・固定手順・evidence記録を追跡。新しいエンジンの複製、候補コピーごとの独立探索、全体探索の優先順位だけ変更する案を検討。既存分岐を再利用する対象フィルタを採用し、計算の対象が曖昧になる優先度方式を退けた。
2. counter/compareの分離を実装。対象外の結果・baselineの進行・全体scheduler位置を隔離。相手辞書共有と比較待ち登録は維持し、後から全体探索へ戻れるようにした。
3. 候補単位の結果差分と実行履歴を追加。全体探索の直近12件とは別に保存し、個別検討の過去記録を全体探索で消さない。checkpoint中の履歴を再起動・インポートでinterruptedに確定する。
4. 開始・停止の並行操作を再検討。保存待ち中もジョブ予約を入れて二重開始を拒否し、初回保存中の停止も計算終了まで待つ。対象照合付き停止を追加。
5. 独立した子担当が実際の終盤状態から複数候補を作り、隔離・再開・保存・バックアップ・入力不正を検査。追加探索の9テスト、旧固定指示APIの4テスト、TypeScript型検査を通過。初回保存を意図的に待機させるテストで二重開始と停止待ちも確認。UIと再読込操作は親担当の結合検証に接続する。

## 配置との接続

対象は選択した作戦、操作は追加計算、結果はその作戦の検査展開と計算履歴。専用の追加探索コンテンツに接続し、全体探索の設定へ候補固有の操作を混ぜない。UI/OSSの配置根拠はfocused_controls側の記録で扱う。この担当はブラウザを操作していない。

## 残る範囲

手順自体を編集した近傍探索、機体速度等を変える感度分析は別条件の計算モデルと結果の由来を定義する必要がある。この変更のcounter/compareは固定された元の構成だけを対象とする。探索完了は限定されたモデルの分岐終了で、実競技での最適性・勝率の保証ではない。
