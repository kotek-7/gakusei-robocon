# 探索・評価の進捗表示で扱う数値

確認日: 2026-10-15。対象は現在のブラウザ版。旧Python版の計算方式や過去の候補数は根拠にしない。

## 競技とモデル

原典は[ABUロボコン2027規則PDF](https://aburobocon2027.id/download/728/?tmstv=1787554332)。公式[配布ページ](https://aburobocon2027.id/rulebook/)からリンクを辿り、Web上の本文とローカルPDFを確認した。配布ファイル名はv1-1だが表紙の版記載はV1.0。[ニュース](https://aburobocon2027.id/news/)に10月6日の重量訂正（2台の合計60 kg以下）が掲載され、[FAQ](https://aburobocon2027.id/technical/)は確認時点で未確定。日本語の用語はローカルの非公式参考訳と照合した。

試合は3分で、終了時の物体状態が採点を決める。TRが搬送し、BRが建設する。アース2段にスカイを載せる。受け渡しは1個5点、設置はL1の下から10・20・40点、L2では20・40・80点。スカイの上面色でその得点の所属が変わり、ムスティカ設置は250点。ムスティカ設置後も試合終了まで続行する（規則3.1、3.6、8）。

`docs/model.md`、`web/src/engine/model.ts`、`discovery.ts`、`evaluation.ts`を照合した。現在はWeb Workerで計算し、IndexedDBへ保存する。`PRODUCT.md`のRuntimeに残る「ブラウザ終了後も計算を継続」は現実装と一致しない。ブラウザ終了後は保存済み位置から再開する。

モデルは整数秒、有限の位置と通路、仮定した性能値を用いる。接触力学、転倒、把持軌道、機体寸法、偶発失敗、通信なしでの実行可能性、審判の接触裁定全体は対象外。候補の発見や評価処理の終了は、実機での成功や最適性の証明ではない。

## 時間と完了を分ける

| 表示 | 意味 | 避ける表示 |
| --- | --- | --- |
| 今回の計算時間 | 実行開始からの実時間 | 試合時刻との共通バー |
| 指定時間 | 今回の候補探索に割り当てた時間 | 全探索の完了予定時刻 |
| 累計計算時間 | `discovery.elapsed`。過去の再開分を含む | 今回の経過として表示 |
| 試合時刻 | 局面の`state.t`。通常の試合終了は180秒 | 計算に180秒かかるとの説明 |
| 評価完了 | 保存済みグラフの集計処理が終了 | 全探索完了、最適作戦確定 |
| 候補範囲完了 | 最短移動・限定待機で生成する範囲を処理済み | 全行動・全方策の網羅 |

候補探索は最短移動と限定した待機を用い、途中で移動目的地を変更する分岐や任意整数秒の待機を含めない。`discovery.complete`は常にfalse。`scopeComplete`がtrueでも、この限定範囲の完了のみを示す。詳細探索の`Search.complete`は全機体構成の全局面を展開した場合だけtrueになる。

指定時間に対する経過率は計算枠の消化率として表示できる。候補探索全体の完了率や残り所要時間は未確定。探索を進めると未処理局面が増えるため、未処理数を固定の分母にしない。

## 累計の数値

| 元の値 | 内容 | 推奨する短い表示 |
| --- | --- | --- |
| `metrics.candidates` | 終了状態に到達した代表手順の件数 | 候補 |
| `metrics.strategies` | 基準展開の分類IDの種類数 | 展開の種類 |
| `metrics.responses` | 各候補に保存した対抗手結果の合計。同じ相手手順が候補ごとに重複する | 対抗手の検査 |
| `metrics.pending` | 候補ごとの未検査共有相手手順の合計 | 比較待ち |
| `metrics.frontier` | 候補探索で発見済みの未処理局面 | 未処理局面 |
| `runs[].remainingChoices` | 選択肢を生成済みの局面で未処理の組合せ | 未処理の組合せ |
| `runs[].commonOpponents` | 全候補に対する固定手順の再計算が終了した共通相手手順 | 共通比較済みの相手 |
| `Search.nodes / expanded` | 詳細グラフの登録済み局面と展開済み局面 | 局面 / 展開済み |
| `Search.runs / totalRuns` | 着手した構成数と設定から決まる全構成数 | 着手構成 |

`bestScores`は相手待機時の自チーム得点の最大値。対抗手がいる場合の点差や保証値とは別。共通条件で検査した点差と、候補ごとの対抗手探索で見つかった点差を混ぜない。

今回の増分には実行開始時の値との差を使う。過去セッションの`newCandidates`、`newStrategies`、`responses`はその実行の増分。履歴は最大12回で、全期間の実行回数ではない。累計値を足し直して今回の成果にしない。

## 評価の段階

`evaluationProgress`は現在の構成と現在段階の進み具合を持つ。`completedRuns / totalRuns`は今回集計する着手済み構成の処理数であり、未着手機体構成を含む全条件の評価率ではない。

| phase | 処理 | done / total |
| --- | --- | --- |
| loading | 対象構成のグラフを読む | 分母なし |
| histories | 履歴を局面順に伝播する | 現在構成の局面数 |
| statistics | 展開分類を集計する | 現在構成の分類数 |
| guarantees | 完全展開した構成の同時行動行列を解く | 現在構成の局面数 |
| saving | 結果を確定する | 分母なし |
| complete | 評価処理が終了した | 処理した構成数 |

段階が変わるたびに分母も変わる。全体の百分率に足し合わせない。保証値の計算は完全展開した構成に限る。履歴数には30,000件の上限があり、到達した場合は統計未完了となる。展開グループ等重みの集計は実大会の勝率ではない。

## 配置の判断と確認記録

開始直後に必要なのは、実行対象、現在の処理、今回の経過、中断の入口。開始した操作の近くと常設の状態表示から到達できるようにする。累計の成果や過去履歴は詳細パネルに置く。現在の処理が目に入らない状態を、説明文の追加で補わない。

確認は2巡。第1巡で公式資料・モデル・実装から指標の範囲を照合し、第2巡でWorker、保存復元、段階更新、候補と全探索の完了条件を追った。本文は人向けの数値定義に絞った。実画面の配置と開始・中断・再開の操作検証はUI担当が別に行う。残る文書課題はPRODUCT.mdのRuntime記述で、この調査の編集範囲外。
