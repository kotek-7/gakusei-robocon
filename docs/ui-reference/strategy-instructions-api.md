# 固定指示の取得

担当: strategy_instructions_api。対象は候補詳細の読み取りAPI。画面と共通Storeの編集は行わない。

## 観察と契約

候補の `plan` は目的、`baseline` と `responses` は実行結果を持つ。ロボットごとの固定指示は内部の `DiscoveryState.runs[run].candidates[].script` に保存され、`publicDiscovery` で除去される。目的・実行結果から指示を逆算すると待機や未完了の指示を失うため、保存された指示を直接取得する。

`candidate.instructions` は `search`, `run`, `candidate`, 任意の `opponent` を受け取る。戻り値の `red` と `blue` は各チームの `[TR, BR]`。相手未指定時の `blue` は `null`。保存された指示が無い場合はエラーを返す。空の2本の手順は有効な保存済み手順として扱う。

候補の探索サマリーは膨らませず、選択した候補だけを取得する。探索中にも読めるが、返却値はネストしたactionまで複製する。相手が候補に対して未評価でも、同じ構成の保存済み相手指示なら取得できる。これは実行結果の存在を意味しない。

## 巡回

1. 内部データと公開サマリーを照合。目的やリプレイからの推測、全候補への指示添付、選択時クエリを比較し、選択時クエリを実装。
2. 取得後の変更と探索継続を検証。返却配列とaction内objectsの変更が保存値へ波及しないこと、継続後も候補ID・相手IDで同じ指示を取得することを確認。
3. 欠落・選択違いを検証。不正な構成番号、別構成、不在候補、不在相手、プロトタイプ由来キー、欠落した固定指示をエラーにした。推測による空手順への置換は不採用。
4. 保存境界を検証。IndexedDB再読込とバックアップ再取込後に同じ固定指示・相手指示を取得した。公開サマリーにscriptを追加しないことも確認。

## 検証と残件

`candidateInstructions.test.ts` の4テスト成功。`npm run typecheck` 成功。API担当としての検証であり、画面操作は統合担当と手順表示担当が実施する。

新しいUI配置を持たないためOSS画面調査はこの枝では実施していない。既存の型付きread query、Runtimeのgetによる共有Store取得、cloneを再利用した。

子担当は無し。共有APIは単一の小領域として実装し、取得・参照独立性・欠落・保存復元を満たした。指示編集、候補をまたぐ比較、指示取得の全件キャッシュはこの読み取りAPIの範囲外。UIは取得中・取得失敗・相手未指定を区別する必要がある。
