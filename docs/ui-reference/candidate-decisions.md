# 検討メモと保存条件の再帰レビュー

2026-10-15、7e41。親の当初の追加案を上限にせず、検討再開・編集取消・保存条件管理を独立領域として検討した。並列枠が埋まっているため、この担当内の小領域は順次巡回した。

## 参照と対象境界

既存の `candidate-expansion-research.md` にあるGodot 4.5-stableのInspector対象ID管理、および添付PDFのsaved viewsパターン69を再利用。現在の候補IDに従属するメモと、候補集合に従属する保存条件の分離はそのまま適用できる。

追加で [VS Code 1.105.0 SearchEditorInput](https://github.com/microsoft/vscode/blob/1.105.0/src/vs/workbench/contrib/searchEditor/browser/searchEditorInput.ts) の `save` / `revert` / `rename` / `registerConfigChangeListeners` を読んだ。設定の保存、保存値への復帰、識別名変更を別の操作として扱っている。ソースのみ確認し、VS Code実機は操作していない。本アプリでは検索結果自体を保存条件へ複製しない。メモ・計算結果・選択経路も条件復帰の対象外。

## 枝と再検討

| 小領域 | 観察した不足 → 採用 | 次巡の再検討 |
|---|---|---|
| 保存条件への復帰 | 条件変更後は別条件を選んで選び直す必要がある → 差分があるときだけ「保存した条件に戻す」 | 名前の未保存変更も保存名へ戻す。メモと再生は変えない |
| 保存条件の削除 | 即削除で戻せない → 保存欄内に直前の削除を取消す操作 | 取消しても現在条件を勝手に適用しない。既存onSaveを通して永続化。削除履歴全体の管理は導入せず、直前1件を対象 |
| 名前の修正 | 名前修正が同時に現在の絞込で上書きする → 名前・条件両方が変更されたときだけ「名前だけ変更」 | 更新ボタンの文言も「名前と条件を更新」「名前を変更」に適用範囲を反映。通常時に補助ボタンを増やさない |
| 作業再開 | 再読込後に絞込は復元されるが保存条件の選択欄は空になる → 初回読込時だけ完全一致する保存条件を選択 | 条件変更後も追従して別の条件名へ自動切替しない。同じ内容の保存条件が複数ある場合は最初の一致を使用し、厳密な履歴とは扱わない |
| メモの保存 | 入力終了後にマウス移動が必要 → 局所Ctrl/Cmd+Enter | IME変換中は保存しない。通常Enterは改行。保存中・差分なしは同じ関数で無効化 |
| 編集を戻す | 下書きの破棄は取り消せない → 保存操作の隣に条件付き「戻した編集を復元」 | 候補IDで保持し別候補へ誤適用しない。新しい編集があると復元入口を隠し、保存成功で破棄した旧編集を消す |
| 未保存メモへの再訪 | 非表示になった候補の下書きは保持されるが探す手段がない | 親へ候補ID別の下書き件数と再訪導線を提案。親の共有ナビゲーション契約が必要 |
| 保存済み判断の履歴 | 手動判断を後から戻したい可能性 | 現行3状態と本文編集で再変更できる。監査履歴・日時列の追加はこの画面の主タスクへの必要性が未確認で保留 |
| 判断のテンプレート | 定型理由を再利用できる可能性 | 利用者の実際の判断語彙が未収集。推測した理由を勝手に埋める機能は不採用 |

操作頻度と手数短縮は設計仮説。ボタン数を成果として数えない。局所取消の記録はセッション内のみであり、再読込後に破棄済み下書きまで復旧する機能はない。

## 検証

`npm run typecheck` 成功。独立したChromeコンテキストで同じ :5187 の終盤174秒探索を実行。下書き破棄→復元、Ctrl+Enter保存、条件の変更→名前だけ変更→保存条件へ復帰、保存条件削除→取消、再読込後のメモ・保存条件・選択条件名の復元が成功。名前だけ変更した後に並び順が保存時の発見順へ戻ることもreadbackした。親のブラウザタブ・データは使用していない。再帰の2巡目は条件変更と名前変更が重なる場合を検証し、その後3巡目で再読込時の選択名復元を確認した。
