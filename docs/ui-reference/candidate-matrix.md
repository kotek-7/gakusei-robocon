# 候補の同条件比較表

2026-10-15。担当範囲は `ComparisonMatrix.tsx`、`comparison.ts` とそのCSS・テスト。親の候補一覧が取り置き集合を所有する。

## 利用タスクとモデル境界

複数候補について、同じ構成・同じ相手手順で赤−青の点差を横並びに読み、気になる結果の実経路へ移る。従来は一候補ずつ選択して相手展開を探す必要があった。操作回数の実測値はない。

`docs/model.md` に従い、`shared` かつ当該構成の `commonOpponents` に存在する手順のみを比較する。同じ相手手順の裁定分岐中の最小点差を使う。共通手順のIDは行、候補は列とし、構成をまたいだ順位を作らない。欠損は未比較。相手待機は区切った参考行。点差は勝利確率や最適性ではない。

## 参照実装と採否

既存調査 `candidate-controls-2026-10-15.md` の選択／実行分離が今回も該当するため再利用。追加で [Godot 4.5-stable scene/gui/tree.cpp](https://github.com/godotengine/godot/blob/4.5-stable/scene/gui/tree.cpp) の `Tree::gui_input`、`ui_accept`、`cell_selected`、`item_activated` を読んだ。4.5-stableの3887–3908行付近では受諾入力の編集／起動を選択とは別に扱う。今回はソースのみ確認し、Godot実機の操作はしていない。

この分離から、点差セルは展開選択、直下の操作列は3D反映・A/B割当とした。Godotのツリー階層やセル直接編集はデータ関係が異なるため採用しない。取り置き対象を同時参照する表であり、候補ごとの排他的なタブやカードにはしない。

| 対象 | 意味・頻度 | 状態・配置理由 |
|---|---|---|
| 表の行と列 | 同一相手手順の結果を頻用で比較 | 共通手順集合は取り置いた同構成候補の積集合。横スクロールで列対応を維持する。構成は別表にする。 |
| 点差セル | 検査展開の選択 | ネイティブbutton、aria-pressedで選択状態を提示。選択だけでは再生画面を変更しない。未比較はボタンにしない。 |
| 相手待機 | 参考結果 | 共通対抗手と分離した最終行。相手待機の点差を共通最小値に混ぜない。 |
| 列の外す | 取り置き対象の変更 | 各列見出しに置き、解除対象をアクセシブル名に含める。全解除は表全体ヘッダー。 |
| 3D・A/B | 選択展開に対する実行 | 直下の一つの操作列。既存コマンドと同じpath/nodeを渡す。pathがない場合は無効。 |
| 選択識別情報 | 操作対象の常時確認 | 操作列に構成・候補・相手IDを明記。長い文字列は折り返す。 |

## 再評価した子課題

- ライブ計算更新中、同構成の候補が異なる共通手順リストを受け取る場合を再検討。積集合に限定し、各セルも個別にshared/commonを検証する二段階にした。
- 選択後に列を外す、共通手順が消える場合、古い展開を実行できてしまう問題を検討。毎描画時に現行行・現行共通集合から選択展開を再解決し、対象がなくなれば操作列を隠す。
- 候補IDが構成間で同じ場合の混同を検討。すべての選択・除外はrun/idの複合キー。構成を別表へ分ける。
- 順位・優劣の色分けは不採用。確認済み手順しか扱わず、裁定分岐の異なる最小経路同士であり、勝利保証の印象を増やす費用に見合わない。

## 検証

純粋ロジック4テスト成功：共通/shared限定、最小裁定選択、構成分離、共通集合の積集合と重複排除、欠損の保持。TypeScript型検査成功。ブラウザでの統合表示・キー操作・3D/A/B割当・狭幅の最終検証は統合担当へ依頼。取り置き集合の保存は親コンポーネントの責務。

## 第2巡：比較表を使って派生した領域別の案

固定した機能数ではなく、比較者の判断が止まる箇所を独立した問いに分解した。実画面を別headless Chromeで開き、終盤174秒の検証局面を作成して候補探索を実行。実データでは5候補・8共通手順、同じ相手IDへの裁定結果が0点と80点に分かれる事例を確認した。

| 子領域 | 観察・問い | 採否と実装 |
|---|---|---|
| 相手の探し分け | 8行でもIDだけでは目的の手順を再発見しづらい | ID検索を採用。意味的な相手手順名の自動生成は保留。現APIは固定相手planを含まず、結果milestonesは相手手順そのものではない。 |
| 候補間の違い | 全候補の最小点差が同じでも、相手別では差が生じる | 「候補間で点差が異なる手順」と「点差の開き順」を採用。構成一致・全候補の証拠あり・2候補以上の場合だけ開きを計算。 |
| 実行できない相手 | 最小値の展開だけを見ても、別裁定の実行不可を見逃す | 全shared裁定を検査した「実行不可を含む手順」フィルター。最小展開だけの検査にはしない。 |
| 裁定の振れ幅 | 同じ相手手順でも0点と80点の結果がある | セルに最小〜最大点差と展開数。選択セル直下に裁定展開selectを置き、実経路に紐付ける。 |
| 原因の追跡 | 3Dへ移る前に不可の機体・時刻・手順を知りたい | 選択裁定の実行不可理由を局所detailsで確認可能にした。全セルへの理由全文の反復は不採用。 |
| 優劣の自動推奨 | 一番大きな数値を推奨候補にしたくなる | 不採用。有限の確認済み相手に対する点差であり、機体工数・偶発失敗・最適性を評価していない。 |
| 既視の証拠への再訪 | 表示を変えても割当対象を追いたい | 選択は候補と相手の安定キー、裁定はnode/path識別で保持。表示フィルターだけでは対象を勝手に変えない。 |

### OSSの追加根拠

[VS Code 1.105.0 hideUnchangedRegionsFeature.ts](https://github.com/microsoft/vscode/blob/1.105.0/src/vs/editor/browser/widget/diffEditor/features/hideUnchangedRegionsFeature.ts) の `setHiddenAreas`、`showAll` と、[diffEditorOptions.ts](https://github.com/microsoft/vscode/blob/1.105.0/src/vs/editor/browser/widget/diffEditor/diffEditorOptions.ts) の `hideUnchangedRegions` を読んだ。左右の一致領域を隠し、明示操作で戻せる構造を、同条件候補間で差のない相手を隠す操作へ適用。文字列diffや勝敗の意味は移植しない。今回もOSS実機でなくソース確認のみ。

表示の件数を「表示数 / 共通手順数」とし、隠した行が存在することを残す。「表示を戻す」で検索・絞込・順序を同時に戻せる。相手待機はフィルターから独立した参考行として残す。

### 第2巡の実操作と再考

独立Chrome・実探索の3候補×8共通手順で確認した。「候補間で点差が異なる手順」は6/8手順となり、表示を戻すと8/8へ復帰。40点のセルを選び、裁定selectで80点・実行不可1件の展開へ切り替え、比較Bへ割当できた。700pxビューポートではmatrixのclientWidth/scrollWidthがともに668pxで、領域外への横溢れなし。

画面を使い直したところ、共通CSSのbutton規則がセルのgridを上書きし、点差・範囲・得点が一行へ混在していた。matrix内だけで表示・高さを上書きし、点差→裁定幅→赤青得点を段に分けて再確認した。また順序の根拠を読むため、相手行に「候補間の開き n点」を追加した。純粋ロジックは6テスト成功、型検査成功。

次の独立枝は相手IDの意味付けと探し分け。別担当へ引き継ぐ。固定相手手順の定義と実際の結果経路を混同しないことが制約。裁定選択の履歴一覧を別途増やす案は、現在の安定選択とA/B割当で再訪できるため、この時点では追加しない。
