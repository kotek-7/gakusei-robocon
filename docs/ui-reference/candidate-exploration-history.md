# 候補の追加探索履歴

担当: exploration_history。親の追加探索担当から、実行後に「何を調べ、何が増えたか」を追う領域を継承。UIは1ビュー1コンテンツに合わせ、操作と進捗の「追加探索」から「探索履歴」を分離した。

## 局所5巡

1. 実装データ確認: before/after.responses は候補responsesの件数。discovery.tsは新規結果のみpushし、既存結果のsharedのみ更新する。runtimeはcheckpoint前にafterを更新して保存、persistenceはactiveSessionをinterruptedとして履歴に移す。追加結果の範囲は保存された半開区間で対応可能。件数不整合や異なる候補にはリンクを作らない。
2. 器の選択: 全履歴×全結果の表を積み上げず、実行選択→その実行の結果に限定。履歴フィルタは結果増加のある実行を絞るために選択の隣。履歴一覧から別ビューを往復せず証拠へ移動する。
3. 再利用: 選択実行のtargetとbudgetから既存コマンドで続行。初めからの再計算と誤認させない「同じ条件で続きから実行」。別候補・別セッション・計算中の無効化を既存コマンドに委ね、探索完了状態も無効化。
4. 結果追跡: 追加結果の元の対応番号、赤青得点、点差、不成立件数を表示し、行から証拠へ直接移動。追加結果内で最小点差へ移動。20件単位の追加表示と結果増加フィルタ。相手手順の検査進捗だけ増える実行もフィルタから落とさない。
5. 保存・不整合: JSONに選択実行、探索ID・候補ID、構成、モデル設定、探索範囲、追加結果をまとめる。履歴だけから探索を復元できない旨、sharedは現在値との注記をファイルへ含める。エラー・読込中・履歴なし・追加結果なし・不正区間を区別。狭幅select/横表のスクロールを調整。境界・中断後追記のhelperテスト4件通過。

## 検証と残り

UIブラウザーは親担当と共有のため親へ委譲。確認経路: 追加探索→実行終了→探索履歴で実行選択→追加結果を選択し点差の一致確認→履歴へ戻りJSON保存→同条件で再開→停止→再読込して履歴保持。狭幅で実行選択と結果表が外側へはみ出ないこと。初期探索の履歴は候補単位ではないため掲載しない。

再実行時の同じ乱数・同じ初期状態の完全再現、探索結果の削除、未保存のクラッシュ分の推定は対象外。APIにない証拠を捏造せず、今回の追加探索の結果追跡・継続操作の範囲を完了とする。子委譲なし（使用中の枠を消費せず親の独立レビュー担当へテスト境界を引継ぎ）。巡回はソース・データ・実装の局所確認であり、5回のブラウザー実操作とはしていない。

親の実画面レビュー後の修正: 実行履歴の「同じ条件で続きから実行」後、追加探索ビューへ移動するcallbackを追加し、制限時間・計算種類を復元する。履歴内から開始して進捗と停止操作を探す往復をなくす。JSON出力は既存saveJSONへ統一した。親から、停止した実行の追加1件と実際の対応3への一致確認が報告された。
