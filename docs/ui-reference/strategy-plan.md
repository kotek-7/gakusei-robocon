# 作戦の順序と機体構成

担当 `/root/strategy_plan`。編集は `strategy-detail/StrategyPlan.tsx`, `plan.ts`, `plan.test.ts`, `plan.css` に限定。子 `/root/strategy_plan/plan_semantics` が固定指示と完了要約の意味を独立確認した。

## 既存機能の確認

候補表を選ぶと右側の MilestoneInspector に完了順が現れ、3Dに表示ボタンで経路を再生できる。表のEnterも3Dを開く。既存の完了順に機体・物体種類の情報はあるが、candidate.planには移動・取得・受け渡し・待機・未実行指示・時刻はない。discovery.ts::publicDiscovery は内部の固定scriptを除去するため、公開候補だけから全指示を読めるUIは作れない。

## 巡回

1. ドメイン確認。候補概要を塔の完成予定として表示する案を棄却。baselineの赤完了イベントから連続同一対象をまとめた順序として表にした。親へ固定script公開の必要性を報告。
2. 対象を再訪する例を確認。スポットで絞っても元の順序番号を保持する対象selectを追加。追加のカード列やタブは不要。同じスポットで建設と反転がある場合もまとめて追える。
3. 順序だけでは機体条件を読めないため、variantの赤能力・積載数・動作時間を横に比較できる属性行へ追加。有効/無効フィルタは能力欄に限定。能力の有効化と実使用を区別する補足を?へ収容。
4. 子の反例レビュー。空planでも搬送等を否定しない文面、未知スポットへの3Dリンク抑止、時刻0や明示高さを落とさない表示を実装。buildだけで物体必要数を推定する案を棄却。
5. 選択変更の確認。候補が変わると前候補の対象フィルタを適用しない。試験3件と全体tscが成功。親の既存画面レビューとscript契約決定を待って統合ブラウザー操作を行う。

この5巡はソース・テストによる実装確認であり、5回のブラウザー実操作を意味しない。統合前のためブラウザー確認は未完了。

## 配置と根拠

添付PDF p.45、51 Inspector/property panelを画像化して確認。選択対象を保ったまま属性を読む構造を採用。折り畳み・モーダル・編集可能風入力は採用しない。`candidate-capacity.md`に記録済みのGodot 4.5-stable InspectorDock::Inspector生成/サイズ拡張と対象変更に追随する構造は、今回の選択候補の構成表示にも適合する。Godot実機の操作は行っていない。

- 順序: 実在する前後関係を表の番号で保持し、記録のない量・時間を埋めない。
- 対象リンク: スポットを3Dで選択する実行操作。識別文字や能力値はボタンにしない。
- 対象select: 頻用する同じスポットへの再訪確認。表示だけを変え、親の候補や展開を変えない。
- 構成: 読み取り専用のラベル/値行。既存の条件編集とは別で、選択候補の探索時の設定を維持。

## 残る枝

固定scriptの公開と表示が親との調整事項。時刻・全移動・動作ごとの結果は別担当の実行記録へ接続する。概要から所要時間や得点寄与を推定しない。統合後は狭幅、対象絞込、候補切替、スポット選択を実操作で検証する。

## 固定指示公開後の追加巡回

6. 親の実画面レビューにより、既存の完了要約では作戦全体の理解に不足すると確認。API担当が保存済みscriptを `CandidateInstructions` として公開した。固定手順を先頭へ追加し、TR/BRの移動先、指定時刻までの待機、操作、物体条件を表示する。赤両機を同時に読み、青の固定相手が取得できた場合は機体selectから読む。同じ手順番号を同時実行と誤認させる横並び時系列表は棄却。
7. `model.ts::demand` と `planner.ts::fixedChoice` を照合。要求は物体種類/面/受渡履歴/保管積層と選択段の一致条件。保管物体を単に数量へ縮約すると条件が欠落するため積層と選択段を表示。blockedのinstructionは0始まりなので表示の1始まり番号へ直接対応させ、選択展開の不成立をその行へ付記する。
8. Variantのspeedsは実数ではなくプロファイル番号と確認し、速い/標準/遅いへ修正。別探索の値をmodel.defaultsから補わない。青手順のない展開へ切り替えた場合、機体フィルタを赤両機に戻す。固定指示と資材条件の試験を追加し5件成功。

追加後の残件は統合ブラウザー検証。APIと接続できたため固定script公開の阻害要因は解消。元の5巡に加えて3巡のソース・実装確認を実施した。子の5巡は意味検証のみ。

## 統合後の再操作

親の統合ブラウザー操作で、赤BRの反転指示と物体条件を読めることを確認。機体構成が指示と実行記録の間を長く占める点が見つかった。

9. 機体構成を `StrategyConfiguration({variant, model})` へ分離。親が末尾の構成セクションに置く。固定手順と結果を続けて読める配置にする。
10. 不成立行に `onSeek(time, robot)` を接続する時刻ボタンを追加。番号と理由を読み、直接その時点の3Dを確認する。不成立が複数時刻なら各時刻へ移動できる。青選択中に青未提供のbaselineへ戻る場合は `activeRobotFilter` が赤両機を表示し、空の青領域に留まらないことをソースで確認。実ブラウザー切替と時刻ジャンプは親の統合確認へ引き継ぐ。

11. 独立した理解レビューで、TRの長い手順を読む間BRの仕事が画面外になる問題を確認。冒頭に赤TR/BRの2行表を追加し、固定指示の種類・件数と移動先/操作地点を同時表示する。各行の「手順へ」で機体を絞り、固定手順見出しへスクロールとフォーカスを移す。長い指示を読む前に両機の役割を確認できる。完了概要は「相手待機時の完了結果」と明示し、固定手順より前へ移動。指示集計の試験を追加。完成塔数や成功数は推定しない。
