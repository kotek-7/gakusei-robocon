# 実行進捗の状態契約

対象は候補探索・全探索・評価の実行中通知。既存の大会モデルや探索範囲は変更しない。

## 1巡目: 通知と保存の分離

観察: `search.changed` は保存完了時にしか通知されず、計算中の更新も約1秒間隔だった。全探索には今回の処理数と予算の公開契約がなく、保存失敗後も評価の状態が `complete` のままだった。

採用: `Search.jobProgress` を任意の一時状態として追加。開始時、250ms以上経過したチェックポイント、保存開始・成功・終了時に通知する。`elapsed` は今回の計算開始からの秒、`secondsLimit` は候補探索に指定した秒数、`unitsDone` と `unitsLimit` は全探索で処理した赤青行動組数と指定予算。全状態空間に対する探索率ではない。処理自体がチェックポイントへ戻るまでは通知できない。

保存状態は `saving` / `saved` / `unsaved` / `error` を区別する。`savedAt` は最後に保存成功を確認した時刻のミリ秒。最終保存中は `phase: saving`、保存失敗時は `saveState: error`。評価の計算が終わっても保存済みとは扱わない。

再読込で架空の実行を表示しないよう、実行進捗は `Store` の一時属性に置き、IndexedDBの概要にも書き込まない。既存保存形式とRPCは維持する。画面側では実行状態を主表示、累計を結果の補助表示に使える。ソルバー初期化はWorker内で実行開始RPCに先行するため、その待機中はUIのコマンド保留状態で表示する。

棄却: 未知の探索空間に対する完了率、未計測の残り時間、処理数を状態数と呼ぶ表示。意味が変わるため採用しない。

## 2巡目: 保存失敗と再読込の検証

実行イベントを追跡する回帰テストを追加。開始時の通知、処理予算1組の実数、最終保存開始、保存成功時刻、一時状態が永続化されないことを確認した。最終保存を保留・失敗させるテストでは保存中の公開状態と、失敗後に評価状態も `error` になることを確認した。全探索で時間スライス内の処理が0件でも、指定ノードが未展開なら継続するようにした。

検証: `npm run typecheck` 成功、`node --import tsx --test src/engine/search.test.ts` 13件成功。画面の配置と実操作はUI担当が検証する。

担当: runtime_progress。子担当 runtime_audit が契約・保存・中断を独立レビュー。追加の探索方式や保存方式の変更は本依頼の対象外。

## 3巡目: 初期保存中の競合

独立レビューでは最終保存中に `status` が先に `paused` / `complete` になる契約を再確認した。保存先を実行中状態に残さないためこの契約を維持し、画面とコマンドは `jobProgress.phase === "saving"` を実行中として扱う。

開始時の保存中にもジョブを予約するよう修正した。同時開始は拒否し、その時点で受け付けた停止は初期保存後に計算を進めず、停止結果の保存まで待つ。競合を再現するテストを追加し、保存失敗を含む関連4件が成功した。子担当の独立確認は変更前の13件が成功、追加の修正必須事項なし。担当範囲の保存・中断・計数契約を満たしたためこの枝は完了。単一の計算処理が長い間チェックポイントへ戻らない場合の更新遅延は残る。
