# 実行中の計算表示

担当範囲: `CurrentJob.tsx`, `EvaluationProgress.tsx`, `live-progress.css`。

## 仕事と配置

計算を始めた直後に、何を実行しているか、今回の上限までどれだけ使ったか、止められるか、保存できたかを判断する。以前の見出し・事実列・説明段落・結果列を、単一の実行領域にまとめた。

| 部品 | 意味と配置 |
| --- | --- |
| 処理名・状態・停止 | 同じ実行を識別して操作するヘッダ。設定・累計と分離 |
| 時間枠 / 今回の行動組 | 左に測定対象、右に実値と上限、その直下に同じ値のメーター。探索網羅率ではない |
| 評価の構成数 | 集計全体の処理単位。現在構成の工程を字下げして従属表示 |
| 現在工程のメーター | engineが公開するtotal/doneのみ。保証値の工程は構成によりskip、次構成で工程が繰り返すため固定stepperは採らない |
| 保存状態・結果へ移動 | 実行領域下端。定期保存で主工程を保存中に変えない。前回評価を残す場合は保存済みの評価と明記 |

## 巡回

1. 既存実装とengineを調査。累計とは別の今回実行領域を採用。段落の再装飾、並列カード群、一律5工程stepperは不採用。
2. CurrentJobを実装しEvaluationProgressを別ファイルへ抽出。子 `live_contract_review` が評価の構成反復、定期保存、最終保存、中断時の前回評価残存を独立レビュー。
3. 子の再レビューと隣接担当レビューから時間の二重表示を除去、行動組の今回範囲を明記、保存失敗時の時刻を前回保存と表示、現工程名だけ読み上げ通知、前回評価に短い識別ラベルを追加。
4. ブラウザーで実保存fixtureに進捗snapshotを注入し計算種別、計数、停止、狭幅を検証。1440pxと390pxで評価の親子表示を目視、390pxでは領域clientWidth/scrollWidthがともに382px。`npm run typecheck`成功。実ジョブ経路は統合担当が別途検証する。
