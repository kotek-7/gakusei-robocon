# 作戦候補の実行不可検査

2026-10-15。対象は `EvidenceDiagnostics.tsx`、`diagnostics.ts`、`diagnostics.css`。

## 観察と構造

既存は選択展開の末尾に `blocked` を箇条書きで表示するだけで、該当局面への移動には全経路を開き時刻を合わせる必要があった。候補探索は `discovery.ts` の `alternatives` で機体・手順ごとに最初の失敗だけを記録する。再試行の総数、永久に失敗した証拠、公式規則による判定ではない。動作順の組番号には実時刻がないため、それから秒数を作らない。

| 部品 | 対象と意味 | 使用・状態・配置の根拠 |
| --- | --- | --- |
| 初回時刻 | 選択展開の記録、常時参照 | 全記録を実時刻でソートした先頭。フィルターで全体の初回情報を変えない |
| 機体・理由 | 選択展開内の絞込 | 時系列表の直上。ネイティブselectでキーボード操作。理由は実文字列で一致判定 |
| 記録行 | 選択、時刻・機体・手順・理由 | 同時刻は機体・手順順。上下/Home/Endで移動。Enterまたはダブルクリックが再生への移動 |
| 前へ・次へ | 絞込内の選択移動 | 表の下で現在位置を併記。端では無効。選択だけで別ワークスペースに飛ばない |
| 時刻を3D表示 | 選択記録の実行 | 時刻をボタンに明記。経路なし・絞込ゼロ件では無効。親が実際の経路選択完了後にseekする |

フィルターと行選択は検査中の一時状態。別の経路に切り替えるとリセットし、以前の理由で新しい結果が消えることを防ぐ。保存する候補や探索結果を変更しない。

## OSS根拠

本アプリの課題「検査結果から実際の対象位置へ移動する」に対し、VS CodeのProblems/marker navigationを参照。

- 公式画面資料: https://code.visualstudio.com/docs/editing/editingevolved#_errors-warnings 。Problems一覧、件数、前後移動とインライン表示を確認。VS Code実機操作はしていない。
- ソース固定版: https://github.com/microsoft/vscode/blob/1.96.0/src/vs/editor/contrib/gotoError/browser/gotoError.ts 。`MarkerController.nagivate` は現在のモデルと位置から `model.move`、選択がなければ終了、異なるファイルなら `openCodeEditor` 後にマーカーを表示。同ファイルでは `showAtMarker`。`NextMarkerAction` / `PrevMarkerAction` はエディタフォーカス条件の操作として登録。close時はエディタへフォーカスを戻す。
- 採用: 記録・位置・前後操作を同じ局所領域に置き、選択と移動を区別。移動先は記録自体が保持する時刻と経路。
- 非採用: ファイル横断巡回、グローバルF8、編集機能。候補内で実行不能記録を調べる仕事には不要。アプリ既存の行キーボード選択を再利用。

## 追加巡回：完了記録からの理解

利用者の追加指示に合わせ、診断だけで領域を閉じず、選択展開の根拠全体を再訪した。

1. 完了記録の意味。`classification.ts::classification` はfinishのplace/flip/take/placeM/takeMだけを保持する。旧「動作順」では移動・受け渡しも含むと誤解されるため「建設・反転等の完了記録」とし、記録に含まない動作を近くに明記。
2. 特定機体の操作確認。機体/動作/場所・物体検索を表の直上に配置。元の組番号を保持し、絞込後の行番号に置き換えない。
3. 相手待機との差を探す。赤機体の同時組列だけを比較し、青のみの追加組による無意味な「差」を除外。最初の相違に移動し、相手待機/選択展開の赤の実記録を併記。これは構造の比較であり、実時間、失敗原因、戦略変更の証明ではない。
4. 新設フィルターの子課題。機体絞込で同時完了した他機体が消えるため、組番号から「全機体の同時完了」をその場で確認できるようにした。フィルターを失わずに文脈を取り戻せる。
5. 新設差分操作の子課題。「最初の相違」を選んでも違いの内容が分からないため、その組の両側の赤の動作・場所・物体を表示。恒常的な二つの全表は狭い領域を占めるので不採用。

OSS根拠の追加: VS Code 1.96.0 `src/vs/editor/browser/widget/diffEditor/commands.ts` の `AccessibleDiffViewerNext` / 前後の差分操作と、公式Source Control画面資料（https://code.visualstudio.com/docs/sourcecontrol/overview）の差分表示を参照。ソースURL https://github.com/microsoft/vscode/blob/1.96.0/src/vs/editor/browser/widget/diffEditor/commands.ts 。差分の位置を選んで両版を確認する操作だけを採用。ファイル編集・revertは計算根拠を変えるので持ち込まない。VS Code実機は未操作。

追加テスト2件が成功。青のみの組を挿入しても赤の完了構造が同じなら差なし、同時性を分離すると差あり、短い側の終了を明示、機体0とスポット0の検索、元組番号を検査。型検査成功。独立ブラウザは接続不可/既存セッション占有で開始できず、UI実操作は統合担当へ依頼。実操作確認済みとは扱わない。

### 機能ツリーと打切り判断

- 選択展開の根拠理解
  - 実行不可の調査: 採用。時刻/機体/理由から記録を選択し再生へ接続。子課題の選択消失・スクロールを修正。
  - 建設・反転等の完了記録: 採用。対象機体/動作/資源の確認、元の同時組を維持。
    - 絞込で隠れる同時機体: 採用。組番号から局所文脈表示。独立保存は不要な一時表示。
    - 相手待機と最初に異なる赤の同時組: 採用。両側の内容を直接併記。
      - 全差分の編集・統合: 不採用。計算記録は編集対象ではなく、LCSによる全行対応は時間と因果の対応を保証しない。
      - 秒数へのジャンプ: このデータからは不採用。milestonesは秒を保持しない。実際のblocked記録からの移動は別枝で提供。
  - 再試行成否の自動断定: 不採用。初回失敗記録と構造完了列だけでは手順と後続イベントを一意に対応できない。
  - 相手展開一覧のグルーピング/比較根拠: 親へ引継ぎ。候補間比較の状態と重なるため共有設計で次の領域担当が調査。

現時点の実装は上記利用タスクに対して完結。独立の領域担当が展開一覧を改めて検討することを妨げず、機能ツリー全体の飽和を宣言しない。
