## 競技と計算結果の境界

`rulebook/Robocon_2027_Rulebook_v1-1.pdf` の本文3.4–3.6、4.2、8、9と `docs/model.md`、`web/src/editors/candidates/evidence.ts` を照合した。

- 試合は180秒。TRの積載上限3個、BRは2個。完成塔はアース2段とスカイ1個。少なくとも共有域1塔を含む2完成塔でムスティカ取得条件が成立し、後の反転で条件を失わない。
- L1の下段/中段/スカイは10/20/40点、L2は20/40/80点。スカイ反転はスカイ得点のみを移す。塔全体の得点を奪う表示は誤り。受け渡しは1個5点、ムスティカ設置は250点。
- モデルは有限通路・整数秒・能力フラグ。接触力学、転倒、把持軌道、寸法、通信なしでの実行可能性、偶発失敗を検証しない。
- 候補探索は最短経路の目的地移動と限定した待機を用いる代表経路探索。任意待機・迂回や全相手方策を網羅しない。候補数や点差から最適性・勝率を表示しない。
- 共通比較は同一構成内の `commonOpponents` と、`shared` が真の対応で成立する。未比較は0点扱いしない。候補ごとに違う相手集合の最小点差を並べるだけでは同条件比較にならない。
- 手順が実行不可になった場合は待機し、その理由を記録する。「別の手順へ適応した結果」と説明しない。

## OSSで確認した構造

Godot `4.5-stable` に固定して、[EditorInspector::edit](https://github.com/godotengine/godot/blob/4.5-stable/editor/inspector/editor_inspector.cpp) と [InspectorDock](https://github.com/godotengine/godot/blob/4.5-stable/editor/docks/inspector_dock.cpp) を読んだ。[公式Inspector説明](https://docs.godotengine.org/en/stable/tutorials/editor/inspector_dock.html) は画面資料と操作の補助として確認した。Godot実機は操作していない。

`EditorInspector::edit` は選択対象変更を検査内容へ反映する。`register_text_enter` は検索入力と内容更新を接続する。`InspectorDock::_prepare_resource_extra_popup` は現在対象に応じて操作を無効化し、`_get_current_resource` は選択履歴の現在IDから対象を解決する。`_prepare_history` は有効な対象をIDで重複除去する。

本アプリへの採用：検討メモ・採否は選択候補に従属するInspectorへ置き、保存キーを探索ID/構成/候補IDとする。検索や並べ替えで行番号が変わっても対象を保つ。選択変更と3Dへの適用は別操作を維持する。候補の計算結果そのものは編集可能プロパティとして扱わない。リソースの保存・履歴管理一式は移植しない。

## 観察した不足と配置の判断

| 利用タスク | 実装から確認した不足 | 対象・配置 | 次巡で確認すること |
|---|---|---|---|
| 大量候補から残す案を決め、翌日再開する | 候補の評価メモ・採否がなく、ハッシュを外部へ控える必要がある | 選択候補Inspectorへ短い評価とメモ。行には状態だけ表示 | 保存/再読込、絞込後の対象、候補更新後のキー維持 |
| 前回と同じ条件で候補群を検討する | 現在のview stateはあるが名前付き条件の切替がない | 集合へ作用する表示設定に保存条件を収める | 更新・削除・解除の区別、消失した相手ID |
| 同じ相手に対する候補の強弱を調べる | 別構成を含む全件表では共通比較の範囲が分かりにくい | 一覧の構成と相手固定を共通比較の根拠とする | 別構成を混ぜない、欠測と0点の区別 |
| 不成立の手順を詳しく調べる | 実行不可はテキストで、別画面に移ると時刻を覚える必要がある | 選択展開内の診断から既存経路・時刻へ移動 | 開いた経路の一致、時刻・機体の引継ぎ |

頻度は設計上の仮説。操作手数の改善値は未測定。保存条件と検討記録は別概念であり、表示条件の解除で採否やメモを消さない。先に現在の候補検討を完結させ、列の自由並べ替えや任意ダッシュボード等の汎用基盤は導入しない。

## 集合操作の再帰レビュー（追加巡）

最初の検討メモ・比較表で候補の再訪は可能になったが、一覧から候補集合を作る仕事を別領域として再検討した。次はコードで確認した不足であり、利用頻度・実測短縮量はまだ仮説。

- 候補を探す → 現在の検索は連続した文字列の一致だけ。`L2 反転`という競技上の条件を表現できない → 空白AND・引用句・除外を導入。
  - 再検討：理由に「L2」とある候補を「L2で建設した」と誤認し得る → `手順:` / `メモ:` / `理由:` / `ID:`の限定検索を用意し、索引の一致領域を返す。
  - 再検討：階層や共有域を固定文言で推定するとモデル変更でずれる → `model-data.json`のスポット階層・所属から生成。相手応答の動作を自候補の手順に混ぜない。
  - 再検討：入力途中の引用符で0件になると編集しにくい → 未閉引用符も現在のフレーズとして扱う。未知のprefixは勝手に解釈しない。
- 候補を順位で絞る → 全構成を点差で一列に並べると同条件に見える → 得点の並び順は構成単位、同点は発見順、未比較は末尾。
  - 再検討：対抗手探索の途中結果を混ぜると順位が成立しない → 既存`worstCommonResponse`を使用し、共通の検査済み相手だけを対象に維持。
- 表示中の候補を比較集合へ移す → 一行ずつのチェックが必要 → 表示集合だけを追加/解除する純粋関数を追加。
  - 再検討：絞り込み後の「解除」で隠れた取り置きまで失う危険 → 非表示キーを保持するテストを追加。比較集合と検査中の単一行は別の状態のまま。
- 条件を往復する → 単一view stateでは前の条件群を再入力 → 名前付き条件を探索内に保存する独立部品を追加。
  - 再検討：復元でメモや再生対象まで変えると作業を中断する → 保存値は絞込・並び順のみ。選択経路・採否・メモは含めない。
  - 再検討：既存条件を上書きしたか分からない → 新規保存/選んだ条件を更新を区別し、保存後の条件変更を表示。削除は保存条件だけを消す。
- 0件から戻る → 以前は検索や構成を変える指示だけ → 親へ検索だけ解除/すべての条件解除と現在の対象範囲の明示を提案。
- 多数行 → 全件DOMと複数スクロールがある。実測性能問題が未確認なので汎用仮想化は今回は不採用。後続担当が大規模実データで再評価する枝として残す。

実装境界は`collection.ts`（検索・順位・集合・保存条件の純粋関数）、`SavedCandidateViews.tsx`（条件保存と検索ヘルプ）、親の`Candidates.tsx`（共有状態・配置）。6件の意味テストと型検査を通過。UIの統合と実操作検証は親・次巡担当へ引き継ぐ。テストは表層の見た目でなく、全角正規化/共有域の根拠/相手動作の混同防止/欠測/非表示の選択保持を扱った。
