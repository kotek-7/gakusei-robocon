# 資源・イベントモデルへの改訂と再評価

対象実装: `3a2cfbf`（基礎モデルの変更は `9645deb`）。大会前提はNHK学生ロボコン2027、競技ルールはABUロボコン2027と同一と仮定する。

## 何を変更したか

- 計時は整数秒を維持するが、判断時点を動作完了・試合終了へ進める。動作途中の任意リトライと時刻指定の待機を外した。待機は他機体の動作完了で解除する。
- 物体のIDを選ぶ代わりに、種類・所有者・色・受け渡し履歴・積み方・取得個数が同じ選択を代表一つにまとめた。初期スカイブロックの取得選択は298通りから3通り（1、2、3個）になった。異なる履歴や積み方は残す。
- 共有在庫は接触時に割り当てる。十分な在庫があるのに両チームが同じ代表IDを指定して競合する問題を防いだ。在庫不足や建設スポットの競合は優先順による結果を分岐する。
- 終了までに完了しない移動、および物体を返さず終了までに完了しないリトライは待機にまとめた。現モデルでは移動途中の接触・通路占有を計算しないため、これらには得点・資源への作用がない。取得・反転・物体を返すリトライは開始時から作用するため残した。
- 作戦分類は物体操作の先頭3組を基準とした。移動・リトライ・物体IDの違いを分類から外し、種類と個数を用いる。詳細な移動・時刻は各試合展開に残す。作戦名は付けない。
- 旧モデルの実行・条件JSON・表示文言の互換処理を持たない。新規保存先は `.explorer-resource-events-2/`。旧 `.explorer/` は削除していない。

これは旧モデル全経路の意味を完全に保存する高速化ではない。時刻指定の待機、途中リトライ、特定IDへの取り合いを含む旧モデルから、作戦検討の対象範囲を変更した。新モデルで定義した選択肢は、計算上限まで網羅的に展開する。

### どの技術判断が比較できたか

残り2秒で赤BRが共有スポットの青スカイブロックを裏返し、青が待機する同条件では、反転2秒は125対45、4秒・8秒は85対45となる。速い反転だけが終了までに再設置でき、赤の得点を40点増やせる。遅い反転も開始時にブロックを保持して青の40点を外す。この差を残したまま、6構成の探索・集計を完了できた。

ただし最悪応答に対する点差下限は反転ありの3段階とも40点だった。速い反転の利点は到達可能な得点・点差の幅に表れ、今回の局面では保証点差には表れない。能力なしは同点が残る。単一の勝率指標だけでは技術判断の差を表せないことも確認できた。

残り6秒でも125対45を発見し、全47展開を25作戦に分類できた。開始10秒は610展開あるが物体操作がなく、分類は1作戦・得点0対0となる。序盤10秒の完了だけで試合全体の作戦価値を判定できるわけではない。

### 途中の改訂から分かったこと

イベント化とID選択の削減だけでは、残り6秒は合計106.5秒でも未完了だった。21,053局面、21,645遷移、DB約605.6MiBに達した。終了までに完了しない移動をまとめたことで43局面まで減った。終盤の膨張の主因は探索実装の速度より、得点・資源に影響しない行動まで区別するモデルだった。

分類変更だけでは試合展開数を減らさない。物体操作に基づく分類を先に適用すると、残り2秒の一覧は320〜512作戦から2〜5作戦に減り、全展開は残った。その後、終了に影響しない移動を省くと展開自体も2〜5件となった。

展開を等重みで数える割合は抽象化に依存する。反転2秒構成の赤が勝つ展開割合は、終盤の無効移動を省く前の50%から80%に変わったが、到達得点集合と保証点差40点は変わらない。この割合を機体性能そのものの評価や実大会の勝率に使ってはいけない。

## 検証

Python 31テストが成功。取得選択の具体列挙と代表選択の資源要求集合の一致、履歴が違う物体の区別、共有在庫の充足・不足、イベント時刻、反転の得点、終了時の選択削減、保存再開、再生、分類を確認した。Webの型検査・ビルド・テストも成功。ビルドには既存Three.jsチャンクのサイズ警告が残る。

実ブラウザで6構成の集計完了、C3の選択、作戦から125対45の局面への移動、3D再生を確認した。390px幅ではページ横幅も390pxで、3Dと得点が表示された。デスクトップ・狭幅の描画も確認した。確認用アプリはポート4175。旧4174のプロセスと保存データは変更していない。

## 残る課題と次の改善対象

1. 180秒全体は30.470秒で2,241局面・5,372遷移、未完了だった。完了した短い局面の比較と、試合全体の作戦探索を区別する必要がある。
2. 判断地点には通路上の中間地点が残る。次は経路制約を維持したまま、取得・受け渡し・建設などを行う地点間の移動にまとめる。到達時刻・進入能力・他機体のイベントへの応答を照合してから適用する。
3. 永続化する状態は依然として具体物体IDと描画用情報を持つ。意味が同じ局面の統合と、代表IDの再生対応を分離する余地がある。今回は競合結果内だけを同一視し、保存済みノード全体の同一視には広げていない。
4. 長い試合では履歴の明示列挙が集計上限に達する。集計用の共有履歴構造と、選択時だけ詳細経路を復元する方式が必要になる。
5. 開始直後にブロックを保持する取得・反転の仮定は、終了間際の妨害効果を強くする。今回の高速化とは分けて、実際の接触・取得・裏返しのどの時点で保持が成立するかを検証する必要がある。
