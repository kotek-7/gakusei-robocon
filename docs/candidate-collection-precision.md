# 作戦候補の検索精度と件数増加の再巡回

2026-10-15。独立担当9。対象は `collection.ts` とその試験。親担当が候補画面を編集しているため、画面の共有ファイルは変更しない。

## 第1巡: 一覧で見た手順をもう一度見つける

- 利用タスク: 一覧に表示された手順を検索へ貼り付ける。建設・反転を含まない候補も探す。
- 観察: 表示の「建設・反転なし」が検索対象に入っていなかった。「建設 6（アース2段）」のような表示句も検索用の語列と異なるため引用句検索で見つからない。
- 採用: `candidateGoalLabel` / `candidatePlanLabel` を公開し、同じ表示句を検索索引にも含める。親が表示側を同関数へ統合する。場所・工程の意味を補う既存の同義語検索も残す。
- 配置: 常設検索欄の対象を一覧と一致させる。新しいボタンやメニューは作らない。
- 検証: 空手順、時刻・2段を含む建設、受け渡し→ムスティカの表示句を引用句として検索する回帰試験が通過。
- 次の枝: 正規表現や完全一致ID構文は導入しない。現在のリテラル検索で表示句を再発見できることを優先する。

## 第2巡: 対応を参照しない並び順の無駄を除く

- 利用タスク: 候補数が増えても発見順・相手待機点差順・未比較順を切り替える。
- 観察: どの並び順でも全候補の共通対応を走査していた。発見順などは結果を利用しない。
- 採用: 共通対応の最小点差順を指定したときだけその値を算出する。既存の構成間非比較・同点時安定順序を維持。
- 検証: 対応配列へのアクセスが失敗する候補でも他の3種類の並び順が動く試験を追加。
- 不採用: 呼出側からの事前計算値を無条件再利用する案。値に対応する相手フィルタが型で保証されないため、異なるフィルタの値を誤使用する危険がある。

## 第3巡: 多数候補と選択集合を再評価

500候補・12工程・32共通対応の合成データでヘルパーの実行時間を計測した。実探索結果ではなく、探索の妥当性や画面の描画性能の証拠には用いない。20反復の中央値は索引作成＋絞り込み10.7ms（最大26.4ms）、発見順0.10ms、共通最小点差順2.38msだった。500候補の半数をメモ条件で絞り込み、表示外の取り置きを失わず追加・解除する回帰試験を追加した。

- 親への統合案: 空の検索では索引を作らず一致とする。検索しない行選択やメモ入力で毎回すべての理由を連結する必要がない。
- 再検討した枝: 全件仮想化、Web Worker化、キャッシュ永続化。実ブラウザの描画ボトルネックを測っていないため採用しない。意味のない先行基盤を作らない。
- 残る枝: 理由検索は現在、相手フィルタにかかわらず候補の全対応が対象。選択した相手だけの理由検索を追加する場合、検索の適用範囲を明示したうえで索引の引数にも相手を渡す必要がある。
- 残る枝: 空手順の表示句は「建設」「反転」という文字を含むため、これら単語の文字列検索にも一致する。工程有無の意味検索は独立した型付き条件が必要で、リテラル検索に隠れた意味を持たせない。
