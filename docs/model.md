# 作戦探索モデル strategy-discovery-3

NHK学生ロボコン2027向け。競技ルールはABUロボコン2027と同一と仮定する。公式規則そのものではなく、規則と有限化の仮定に従う計算モデル。原典PDFと過去のレビューは変更しない。

## 詳細モデル

状態は時刻、4台の位置・実行中の動作・進入履歴、53個の競技物体の所在・段数・所属・色・受け渡し履歴、ムスティカ取得条件と得点履歴。アースブロックは各20個、スカイブロックは共有12個、ムスティカは1個。各物体の所在は一つに限る。

位置と通路は `explorer/model/field.py` の有限グラフ。移動時間は距離を走行速度で割って秒へ切り上げる。取得・設置などの時間も正の整数秒。数値項目は独立の速い・標準・遅いの3段階。能力フラグから速度や技術工数を推定しない。

| 操作 | 条件と変化 |
|---|---|
| 移動 | 役割・能力・規則設定で許される通路を通り、完了時に位置を更新 |
| 取得 | 積載・混載・支持条件を満たす物体を開始時に保持。同等な在庫は種類・個数・属性で選択 |
| 床経由の受け渡し | 自陣受け渡しエリア。TRの解放時に規則設定に従って加点 |
| 直接受け渡し | 同じ物体についてTRとBRが同期した選択をした場合のみ |
| 設置 | アース2段、その上にスカイ。完了時に塔へ解放 |
| 反転 | 開始時にスカイを保持して採点から除外し、完了時に自色で設置 |
| 持ち直し | 自分の最上段アース、または移設設定が許すスカイ |
| ムスティカ | 取得条件・能力・所在条件が必要。中央柱への解放後に加点 |
| リトライ | 動作終了後のみ。復帰位置と保持物の扱いは規則設定に従う |
| イベント待機 | 次の非待機動作完了、または試合終了まで待つ |
| 1秒待機 | 1秒後に再判断。連続して整数秒の開始遅延を表現する |

通常動作の途中で方向を変えたりリトライしたりしない。終了までに完了しない移動と物体を返さないリトライは待機にまとめる。取得・反転・物体を返すリトライは開始時にも影響があるので、終了時に動作中になる選択を残す。

双方は同じ局面を観測して行動を選び、相手の今回の選択は見ない。移動時に資源を予約せず、取得・反転の開始時に競合を処理する。共有在庫が不足すれば、設定した優先順の結果を分岐する。同じ塔の操作は排他。次の動作完了か試合終了まで時間を進める。

## 選択肢を保持する候補探索

各ロボットが空いたとき、詳細モデルの合法な資源操作を全て生成する。取得個数、混載、床への受け渡し、対応する直接受け渡し、1個単位の設置と持ち直しを残す。TRはBRの建設先に拘束されず、BRも塔の完成まで同じ目標を続ける義務を持たない。リトライは詳細モデルで許可されたものを含める。

移動は資材置場・受け渡しエリア・建設スポット・ムスティカ柱などの作業地点を目的地に選び、最短所要時間の経路を完走する。途中で目的地を変える分岐は生成しない。移動全体が残り時間に収まらない目的地は省略する。待機は次の動作完了・試合終了と、反転可能な地点で終了直前の反転開始を待つ選択に限定する。任意の整数秒待機や経路の迂回は詳細全探索側に残る。

建設目標からの従来の方針は、行動リストの並べ替えだけに使う。混載で必要資材を運ぶ、両者がそろえば直接渡す、既存塔の完成を優先するなどの順位も候補除外には用いない。有望な完走経路と古い未探索局面を交互に進める。4台の行動リストの直積はカーソルから1組ずつ生成し、全直積をメモリに展開しない。不一致の直接受け渡しは合法な組合せではないため除外する。

相手待機で自チーム候補を生成し、候補のロボット別手順を固定して同じ生成器で相手の対抗手を探索する。発見した相手手順は同じ構成の候補全体へ共有する。双方の手順を固定した再計算で全裁定分岐が終わったものだけを共通比較済みと数える。手順の実行条件が成立しなければ待機し、その局面を記録する。別の作戦への自動差し替えはしない。相手の各同時選択も遷移前の同じ局面から決める。

候補は終了状態に到達した具体的経路の代表例。同一状態への複数経路はグラフに残すが、全経路の候補行への列挙は行わない。全ての相手方策や状況に応じた方策の最適性は保証しない。

## 詳細な全探索と評価

詳細な全探索は同じモデルの全ての行動の組合せを列挙する。1秒待機も対象にするため、有限でも180秒全体の完了は実用時間内に保証しない。候補探索の完走と全探索の完了は別であり、候補を保存しても局面を展開済みにしない。

得点は受け渡し履歴、塔のアースの所属・スカイの色、設置済みムスティカから計算する。ムスティカ取得条件は設定に従って同時保有または完成履歴で判定し、一度成立した条件は保持する。勝敗は得点、ムスティカ、スカイ数、L2/L1個数の順。残る同点は審判未決。

完全展開した構成に限り、同時行動の行列を線形計画で解く。赤の勝利確率の保証を優先し、その保証を維持する点差の保守的下限を表示する。競合結果は不利なものを考慮する。分類した作戦だけに相手の行動を限定しない。

## 保存・分類・API

SQLiteには正規化した全状態のキー、全ての入出辺、列挙カーソルを保存する。時刻が必ず増える有限DAG。同等な将来を未証明の状態は統合しない。

候補探索には、物理状態のノードIDに加えて移動目的地・待機期限・固定手順の実行位置を持つ探索状態、未生成組合せのカーソル、探索ジョブ、到達辺を保存する。全裁定結果を継続可能な探索状態にする。1組の展開結果とカーソル、候補・相手手順登録を同一トランザクションで確定し、中断後は途中局面から再開する。構成、候補発見、対抗手探索、共有比較に順番に計算時間を割り当てる。

- `POST /api/searches/{id}/discover`：`{"seconds":10}`。整数1〜86,400秒の予算でバックグラウンド実行。既存の停止APIで中断する。
- 概要の `discovery`：累積時間、構成別の候補・未検証数・実際の得点・経路、未探索局面数、生成済みの未計算組合せ数、共通比較済み相手手順。`complete` は常にfalse。最適性を表す値を返さない。
- `POST /api/searches/{id}/start`：従来の詳細な全探索。行動組合せ数の予算を用いる。
- 既存のグラフ・局面・再生APIで、候補の保存経路をそのまま表示できる。

作戦分類は試合全体の設置・反転・持ち直しの完了順序と同時性を用いる。物体IDを種類・所属に置き換え、移動・搬送の違いは詳細展開側に残す。分類版は `match-milestones-v3`。IDは構造のハッシュで、意味的な名前を付けない。ロボット別手順の候補IDと、実現した試合展開の作戦IDは別に保存する。

厳密な履歴の集計は時刻付き非待機イベント列を使う。展開グループは絶対時刻を除いた構造。履歴伝播には30,000件の上限があり、到達時は統計未完了とする。候補表はこの履歴集計を待たずに利用できる。

## モデル外

接触力学・転倒・把持軌道・機体寸法・通信なしでの実行可能性・偶発失敗・審判による接触裁定全体は扱わない。受け渡し床の収容密度は個数管理。代表機体の通路と操作可能性を能力フラグで与える。ルール未確定部分の設定は仮説であり公式裁定ではない。
