01試合のルール

ABUロボコン2027「ヌサンタラのムスティカを求めて」。11m四方のフィールドで赤と青が3分間（180秒）対戦します。各チームは運搬ロボットTRと、完全自動の建設ロボットBRの2台。TRが地面の資材を受け渡しエリアへ運び、BRが高台にタワーを建て、最後にムスティカ（バレーボール）を中央柱へ奉納します。

03フィールドの有限化

連続した床をそのまま扱うと探索できないため、アプリはフィールドを44個の地点と44本の通路のグラフに置き換えています。地点は作業できる場所（保管エリア・スカイ置場・受け渡しエリア・建設スポットなど）と、その間の中継点です。通路には「平地」「スロープ」「L1階段」「L2階段」の種別があり、機体の能力フラグで通れるかが決まります。

地点をタップすると到着地になります。各通路の所要時間は「距離 ÷ 走行速度」を秒に切り上げた整数（最低1秒）。BRは一度高台に上がるとグラウンドへ降りる通路を使えず、規則設定でスロープ利用を許さない限り南北の地上通路も通れません。

04局面と同時行動

局面（状態）は「時刻、4台の位置と実行中の動作、53個の物体の所在・段・所属・色・受け渡し履歴、マンデート成立、受け渡し得点」の組です。時間は1秒刻みですが、毎秒計算するのではなく、空いている機体が行動を選び、次にどれかの動作が終わる時刻まで一気に進めます。

遷移を1つずつ進める transition.ts successors()
移動取得・受け渡し設置イベント待機現在時刻

標準スペックで、赤は「床経由の受け渡し」、青は「直接受け渡し」で自陣側スポットへ2段積む手順を1本だけ再生しています（例示用に固定した手順）。実際の探索は、各判断時点で選べる行動をすべて分岐させます。

同時に選ぶ相手の今回の選択は見えない

4台は同じ局面を見て、それぞれ行動を選ぶ。遷移は「赤2台の行動 × 青2台の行動」の組で表す。

イベント待機誰かの動作が終われば再判断

待機中の機体は、他の機体の非待機動作が完了した瞬間に解放される。上の例で赤BRが38秒で一度起き、まだ足りずにもう一度待つ様子が見えます。

直接受け渡し両者が同時に合意したときだけ

TRの「渡す」とBRの「受け取る」が同じ物体で同時に選ばれた組だけを合法とする（matched()）。

同等な物体属性が同じなら1つの選択肢

保管エリアの20個のアースを個別に区別せず、種類・所属・色・受け渡し履歴・積み位置で同値にまとめる（demand()）。

競合の裁定分岐 rules.conflict

共有スカイが残り1個のとき、赤TRと青TRが同じ瞬間に取りに行った場合。移動中は資源を予約せず、取得の開始時に在庫を割り当てます。

同時取得・操作の競合

負けた側は動作を開始できず「阻止」として記録され、1秒待機になります。評価では、この裁定分岐のうち赤に不利な結果を採ります（第7章）。

05候補探索：選択肢を捨てずに順番だけ付ける

「候補を探す」は、詳細モデルの合法な行動を全部生成したうえで、計算しやすいように2つだけ制限をかけた探索です。移動は作業地点までの最短経路を完走（途中で目的地を変えない）、待機は次の動作完了か試合終了まで（反転できる地点では終了直前の反転開始を待つ選択も追加）。取得個数・混載・床か直接か・建設先の切替は全部残します。

4台の選択肢の直積とカーソル util.ts combination()

ある判断時点の例（選択肢は抜粋）。全組合せをメモリに並べず、カーソル番号を混合基数として1組ずつ取り出します。最後の機体が一番速く回ります。

展開の順番：有望な完走と古い未探索を交互に discovery.ts expand()
偶数手：有望な経路を続ける奇数手：最も古い未完了局面未生成の組合せ終了局面＝候補

偶数手は直前に生まれた子（なければ点差の優先度が最も高い未展開局面）を掘り、試合終了まで早く到達して候補を出します。奇数手は最も古い未完了局面のカーソルを1つ進め、取りこぼした分岐を少しずつ埋めます。図は分岐数と点差を擬似乱数で作った模型です。

建設目標（どのスポットに建てるか、ムスティカを狙うか）から作る従来の方針は、行動リストの並べ替えだけに使います。「既存塔の完成を優先」などの順位で候補を除外しません。候補は終了状態に到達した具体的経路の代表例であり、最適性の保証ではありません。

06対抗手と共通比較

候補探索は3種類のジョブを順番に回します。構成（能力と数値の組合せ）ごとに独立した run があり、時間は run を巡回して配分し、各 run の中では baseline → counter → compare の順に1手ずつ進めます。

baseline赤の候補を見つける

青は待機させ、赤2台の選択肢を探索。試合終了に届いた経路から、ロボット別の手順を取り出して候補 P-… として登録します。

counter候補を固定して青の対抗手を探す

赤の手順を再実行しながら、青を同じ生成器で探索。優先度は青−赤の点差。見つかった青の手順は O-… として同じ構成の全候補で共有します。

compare両方固定で全裁定分岐を検査

候補×相手手順の組を、競合の裁定分岐まで全部計算し終えたものだけ「共通比較済み」と数えます。

手順は「移動先へ向かう」「この地点でこの操作をこの属性の物体に行う」の列です。再実行中に条件が成り立たなければ、その機体は待機し、阻止された局面を記録します。別の作戦への自動差し替えはしません。確認済みの点差を「保証値」とは呼びません。

07詳細な全探索と評価

「詳細な全探索」は、候補探索の制限を外し、1秒待機や途中の分岐も含めて全行動の組合せを列挙します。局面は同一状態を統合した有限DAG（時刻は必ず増える）として IndexedDB に保存され、全分岐を処理したときだけ「探索完了」になります。180秒全体の完了は実用時間内に保証されません。

完全に展開できた構成では、終了局面から時刻を遡り、各局面で「赤の行動 × 青の行動」の行列ゲームを線形計画（HiGHS の WebAssembly 版）で解きます。値は3種類です。

1局面の行列ゲーム evaluation.ts / linear.ts matrixValue()

各セルは、その行動の組の行き先局面の値です。裁定で分岐するセルは、赤に不利な方を採ります。赤は行動を確率 p と 1−p で混ぜ、青が最も困る列を選んでも得られる値を最大にします。

勝利確率の保証（下限）
負けない確率（上限側）
保証を保つ点差の下限
赤の混合戦略

線は「青がその列を選んだとき」の赤の勝利値。太線（下側の包絡線）の最高点が保証値です。点差は、勝利確率の保証を落とさない p の範囲の中で最大化します。実装は1回のソルバー呼出しを2秒で打ち切り、最適解が出なければ保証値を確定しません。

分類作戦は完了順序の構造で分ける

試合全体の設置・反転・持ち直しの完了順序と同時性を、物体IDを種類・所属に置き換えてハッシュ化。意味的な名前は付けません（browser-milestones-1）。

集計展開グループを等重み

絶対時刻を除いた構造が同じ試合展開を1グループとし、グループ間・グループ内を等重みで勝率と点差分布を出します。実大会の勝率ではありません。

上限履歴は30,000件まで

経路履歴の伝播が上限に達したら統計未完了と表示。未探索・打切りを0勝や到達不能とは扱いません。

08モデルが扱わないこと

  • 動作は必ず成功する前提。接触力学・転倒・把持軌道・機体寸法・偶発的な失敗は扱いません。
  • 位置と経路は代表機体の有限グラフ。経路の迂回や途中の方向転換は詳細全探索側だけ。
  • 受け渡しエリアの床の収容密度は個数で管理。
  • 通信なしで実際にその手順を実行できるかは検証しません。
  • 審判による接触裁定全体、違反による強制リトライの判断は対象外。
  • 数値スペックの初期値は仮定であり、実機の測定値ではありません。
