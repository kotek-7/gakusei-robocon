# 作戦探索器のモデル仕様案

状態: 2026-10-13、Q34までの回答を反映した仕様案。各方針と全体像についてgoを受領。実装仕様は model.md に記録。具体的な遷移表・分類アルゴリズム等は下記方針に従って技術設計する。

## 合意済みの目的と境界

機体構成の整合する組合せと、その下で成立する双方の詳細な試合展開を探索する。固定作戦の総当たりは廃止する。構成・作戦・単一展開の各層を多面的に評価し、同じ計算状態をグラフと3Dで確認する。機体性能より能力の採否を含むスペックを重視する。

移動、取得、受渡し、設置を分解する。全盤面を観測可能とするが、相手が今回選択する行動は事前には見えない。探索中断・保存・再開を許容する。調査・解釈、AIによる作戦命名や推奨、ユーザー用枝刈り条件作成UIは設けない。

分類は行動・状態遷移の構造に基づき、正確な秒数は経路に残して分類から外す。前後関係・同時進行・競合結果を残す。モデル上の対称性・独立性を確認できる場合だけ差をまとめる。比較する構成で分類定義を共有する。作戦は分類階層の機械的な固定基準による切断層。切断調整UIは作らず実結果を見て実装を改訂する。

勝敗を第一、得点差を補助とし、経路数、点差分布なども保持する。相手は複数構成。分類としての作戦とゲーム理論上の行動方針は別の概念として管理する。

### 原典だけでは確定しない論点

- リトライ保持物: 5.1.1は初期位置へ戻す、5.3.2は保持可。どちらかを公式裁定として断言しない。
- BRスロープ: L1の一般的説明ではスロープあり、BR専用4.3.2では階段への進入を記載。切替可能な規則解釈設定として分離する。
- Skyの位置変更: 同じ塔上の姿勢変更と、別地点への移設の許容範囲は追加確認が必要。
- 同時到着・同時取得時の勝者: 固定の赤優先という公式規則は確認できない。
- 搬送済みブロックを戻して再搬送した場合の再加点、奉納済みMustikaへの相手操作などは別途解釈が必要。
- 資格の成立判定タイミング、混成塔のタイブレーク帰属、直接受渡し時の解放判定は、モデルで具体的な解釈を明記する。

未確定解釈は設定で切り替え、各設定に条項・解釈と版を記録する。同種の未確定事項も設定対象にする。未確定解釈は機体能力ではない。規則プロファイルの違いを混ぜた総合勝率を作らず、別条件として保存・比較する。

## 2. 共通の状態モデル案

規則プロファイルR、有限の能力・数値候補ドメインD、幾何グラフG、初期配置I、時間単位Δを探索条件に含める。

構成 c ∈ D に対して C_R(c) を満たすものを列挙する。能力不足で得点できないことは規則違反や構成矛盾とは異なるので、弱いだけの構成を自動削除しない。導出できる能力を独立変数にして重複列挙しない。

局面 s = (t, robots, objects, qualifications, transferLedger, retryHistory, occgoupancy)。

- robots: 各機体の地点/経路区間、保持物、操作フェーズ、開始・完了時刻、動作中の対象、必要な形状・到達属性。
- objects: Earth40個、Sky12個、Mustika1個の所在、配置者/色、支持関係、接触・保持状態。撤去・落下・リトライで保存される一意性も管理。
- qualifications: 永続資格。取得時刻は分類に必要な経路メタデータとしても保持。
- transferLedger: どの搬送が加点済みか。再加点解釈を変えられるよう現在在庫の個数から推測しない。
- retryHistory: BRのL1進入済みフラグ等、未来の合法行動を変える履歴。
- occupancy: 経路・操作領域の占有。到着前の塔の予約で所有権を与えない。

物体IDは表示・履歴のため保持する。同一物体として入れ替え可能かは、位置、属性、加点履歴、未来の選択肢まで含めて別途証明する。持っているEarthの色/帰属をロボットの所属から推定しない。

## 3. 機体構成の変数候補

以下は能力として記述する案であり、すべて独立なbooleanにするという意味ではない。

| 系統 | 変数候補 | 制約・注意 |
|---|---|---|
| 走行 | 平面、GND–L1スロープ/階段、L1–L2階段、荷物別の通過可否 | 上り下り・積載で能力が異なり得る。規則上の役割制限と分離 |
| 積載 | TR 0〜3、BR 0〜2、混載パターン、Mustikaとの混載 | 0はそのブロックを扱えない構成。Mustikaとblock上限の関係は明記 |
| 取得 | Earth/Sky/Mustika、床・積み上げ位置からの取得 | 到達範囲、把持方向、保持可能姿勢を有限属性化 |
| 受渡し | 床置き/回収、直接受渡し | 直接受渡しは両機体の同期動作 |
| 建設 | 下段・中段Earth、Sky設置、再把持/反転 | 段ごとの到達範囲・支持制約 |
| 奉納 | Mustika取得・受渡し・中央柱への設置 | 資格、役割、到達位置の論理積 |
| 所要時間 | 経路区間・積載・操作別の正の値 | ルールから値は出ない。指定された有限候補を探索 |
| 開始条件 | 開始枠割当、Earthの有限初期配置候補 | 規則上許される連続配置を無制限に列挙しない |

数値スペックは走行・取得・設置・反転など各項目で独立した fast / normal / slow の3段階とし、構成探索で組み合わせる。一式の3プロファイルには限定しない。各段階の数値は編集可能な仮定であり、実測値と誤認させない。能力採用による速度低下や重量増加を自動仮定する機能、任意の性能依存関係を設定する機能は設けない。ルールと操作成立上必要な制約は維持する。

例: 「L2へ行くか」は行動選択。「L2へ合法な経路で到達できるか」は構成と経路から導出する。「GND–L1階段を使わない」は、BRに別の合法経路がなければ上がれない構成になる。独立にON/OFFできる任意の便利技術とは限らない。

## 4. 行動と時間の案

行動を move(edge)、pick(object/subset)、release/receive、place、regrasp/orient、retry、wait に分ける。対象位置・保持能力・所有・資格・必要領域の条件から合法性を生成する。複数同時把持は、それを可能とする構成だけに与える。解放と把持開始は状態変化イベントとして得点に反映する。

合意済みの有限化:

- 操作地点・経路区間・操作姿勢・初期配置は有限候補とする。任意曲線・全姿勢・連続座標での全配置は探索しない。
- 時刻は1秒単位。所要時間の換算・丸め規則はモデル仕様に明記し保存する。
- 通常の判断機会は行動・移動区間の完了時。実行中の通常動作はフェーズ終了まで継続する。毎秒すべての行動を選び直さない。
- 待機候補の初期案は1・2・5・10秒（会話中の例に基づく設計値）。待機は指定時間の終了または他機体の状態変化で再判断できる。
- 途中に判断へ影響する状態変化がない連続待機は正規化する。同じ開始時刻を生む待機の分割表記だけを別経路として数えない。状態変化の前後で選択が異なる履歴は残す。
- 固定待機候補と再判断規則はモデルの範囲を定める。候補待機の反復で毎秒開始を再現する場合は単なる重複除去であり、分岐削減を過大に主張しない。反復制限で開始時刻を省略する場合はモデル制約として明記する。
- 任意リトライによる中断は通常動作の変更と分離する。1秒境界で要求できる仕様とし、その分岐をイベント飛越で消さない。
- 同時選択は同じ開始前状態に基づく。自チームの直接受渡しは両機体の同期操作として扱う。
- 次の意思決定機会/動作完了まで進める。t=180をまたぐ動作も許可し、終了時の接触・保持状態で採点する。t=180には新規動作を開始しない。

### 同時競合

T_R(s, jointAction) は一般には単一の状態ではなく、許容する次状態の集合として定義できる。

- 出発しただけで共有物体を予約しない。移動と操作の競争を分離する。
- 独立な同時完了はまとめて反映。作用が競合する場合だけ順序・結果を分岐。
- 「操作開始前に既に取られた」場合は取得失敗として在庫を二重消費しない。
- 同時接触の赤優先/青優先等はモデル上の競合ケース。確率未指定なら50%と決めない。
- 干渉禁止のため双方の要求を同時実行できない場合、何が中止・待機・裁定となるかを規則プロファイルで明示。単純な取得順分岐だけで実際の接触裁定全体を再現したとはしない。

### 成功・失敗の範囲

初版は操作成功時の能力差を探索する。意図的に選べるリトライは含め、偶発的な落下・故障とその確率モデルは含めない。同時競合の結果分岐は偶発故障とは別に扱う。

## 5. 探索器の契約案

- 構成列挙: 有限ドメインの制約充足。整合する赤/青の組ごとに同じ規則・初期条件で探索。
- 展開列挙: 合法な共同選択と競合結果を列挙。バックトラックと状態メモ化を使う。
- グラフ: 全行動ラベル付き多重辺を保持する。制御ノードと解決イベントを分ける場合は種別を明示。時間の進まない内部遷移には位相順序を与えて無限循環を防ぐ。
- 同値統合: 未来の合法行動と遷移・評価に必要な全属性を含む状態キー。同一時刻必須。単に得点と塔が同じという理由では統合しない。
- 経路: 統合先に単一の親だけを保存しない。複数入辺・行動多重度を保持し、厳密経路数を任意精度整数で集計する。
- 分類: 同じ局面への異なる到達履歴で分類特徴が異なる場合、分類用の履歴要約を状態と別に伝播する。終端局面数から作戦分布を推測しない。
- 枝刈り: 制約不成立、証明できる重複計算の削減を優先。最適値だけを保つ枝刈りと、分布・経路数を保つ枝刈りを混同しない。対称性縮約も多重度を復元できる場合に限る。
- 再開: 未展開ノードと途中の行動組合せカーソル、構成列挙カーソル、規則/モデル/分類の版を保存。
- 完了判定: 対象の構成・初期状態・全分岐について未展開がなくなったときだけ完了。部分結果の探索済み割合は全体数が不明なら出さない。
- 公平な比較: 同じ予算で打ち切っても同じ網羅率とは限らない。未探索は到達不能や0勝として扱わない。

## 6. 評価方針

作戦分類群は閉じた行動方針とは限らない。「この群の中だけで相手の最善応答を計算する」と、群外の対抗手を消して誤った保証を作る可能性がある。まず完全な行動ゲーム上の評価と分類群の統計を別々に計算し、群への帰属方法を定める。

同時行動ゲームは完全情報の逐次max-minへ置き換えない。相手の今回の選択を観測せず、混合方針の必要性を含め評価する。勝敗優先・得点差補助、審判未解決、競合ケースの扱いを明文化する。標準集計は同一視でまとめた展開群を等重みとする。厳密な経路数・経路単位の勝敗割合も併記する。双方を実大会での勝率や最善応答の保証値とは区別する。

相手構成別の結果を基本とし、全体には最悪値・最良値・分布を表示する。相手の出現頻度、総合勝率、一つの総合順位を仮定しない。競合には勝手に確率を付けず、保証値では不利な競合結果も考慮し、ケース別結果を保持する。

## 7. 既存実装との違い

- abu2027/model.py: 位置・経路・個体IDなし。搬送/建設がマクロ。塔を出発時予約。任意リトライ、再配置、直接受渡しを独立操作として扱わない。
- abu2027/search.py: state_keyは時刻・在庫・塔・資格・実行中job等を持つが、合流前の履歴は保持しない。到達終端状態数は試合経路数ではない。探索要約のみで保存/再開グラフではない。
- abu2027/game.py: 同時行動の利得行列を解くが目的は期待得点差。勝敗第一の評価ではない。
- web/src/simulation/engine.js: chooseが固定方針で一つの行動を選ぶ。4台の順次dispatchが変更中の状態を参照する。新しい全分岐エンジンの土台としてそのままは使わない。

## 8. 実行形態と実装時の確認

ローカル計算プロセスとWeb画面を分離する。ブラウザは設定・探索操作・グラフ・3Dを担当する。ブラウザを閉じても計算は継続し、探索状態をローカルに保存する。計算プロセスの停止後も保存済みチェックポイントから再開可能にする。サーバー配備は初版の前提にしない。

以下は実装者が具体化し、実装文書・テストに根拠を残す事項。ユーザー未回答を理由に恣意的な固定作戦や候補削減で代替しない。

- 能力変数、有限な位置/経路/初期配置候補、各行動の前提・効果と原典の対応。
- 時刻丸め・待機正規化・同時完了・リトライの厳密な遷移規則。
- 同値状態のキーと保持すべき履歴・多重度、終了状態の採点。
- 構造分類の具体的な計算手順と固定切断基準。探索打ち切りの度に作戦IDが意味を変えないよう定義を版管理する。
- 勝敗優先/得点差補助の同時行動ゲーム評価と分類群との対応。未探索が残る場合の保証可能範囲。
- 保存形式と原子的チェックポイント、計算予算、画面の大規模グラフ閲覧方法。

検証では、小局面の素朴全列挙との一致、合法性・資源保存、同時選択での情報漏れ防止、同値統合後の経路数・分布、停止再開の同一性、得点と3Dの一致を確認する。180秒・全構成が実用時間内に完了することは現時点で未検証。打ち切りを完成扱いにしない。
