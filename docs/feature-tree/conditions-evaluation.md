### 子機能

- 能力と数値の独立選択 — 既存実装。コードでは選択肢を最低1つ残し、組合せ数をBigIntで計算している。
- 数値編集と別ワークスペースへの往復 — 既存実装を確認。終了時刻を180から120へ編集し、評価 → 条件の往復後も120が残る。新しい探索の作成はこの周では実行していない。
- 変更箇所だけの表示・元条件との差分 — 未着手。2つの探索を作る前の照合に有用。現在の対象タスクは条件表で値を直接確認できるため、専用差分表示は優先度で持ち越す。
- 自動再計算 — 打切り。能力・数値の複数変更で組合せが増えるため、明示的な作成・計算を維持する。
- 初期局面JSONの入力検証 — 未着手の追加レビュー。読み込み経路とエラー表示は存在するが、この周では不正JSON・モデル不整合の実操作は未検証。

## 評価 — 実装済み（既存機能をレビュー）

保存済み候補探索は評価未計算。評価ワークスペースは未計算を明記し、同じ画面の計算パネルに「評価を計算」があることを確認。

コードでは比較対象の初期局面・終了時刻・ルール・配置の一致を検査する。相手構成の照合では能力と実際の数値を比較する。結果の網羅状況、180秒未満の評価、保証未確定を区別する。これらの数理的正確性全体を、このUIレビューで検証したとは扱わない。

### 子機能

- 計算開始と未計算表示 — 既存実装。F6で評価を実行し、0.1秒・1/1構成の処理完了を確認。4展開グループについて「発見済みの範囲」「途中」「保証未確定」を維持している。ボタンとF6は同じ `job.evaluate` コマンド。
- 評価結果から局面を開く — 既存実装をコードで確認。該当結果と経路の全組合せは未検証。
- 比較条件の差分表 — 未着手。現在は不一致の警告と条件ワークスペースで確認する。2探索の異なる条件を多数扱う実タスクを次のレビューで検査する。
- 長い説明の折り畳み — 未着手。警告・未完了の表示まで隠さない設計が必要で、未計算画面だけを根拠に全体を改修しない。

ルートは飽和ではない。結果表の値や未完了区別の破綻は確認されていない。ただし評価完了時のトーストが「評価: 指定時間で停止」と表示され、計算パネルの「評価の計算完了」と食い違った。統合時に、評価の正常終了理由を `completed` として通知するよう修正した。計算完了と探索の網羅性は別に扱う。


## 2026-10-15 条件・評価の操作密度

### 確認した前提

READMEとモデル仕様を読み、能力と数値の独立した組合せを探索する用途を確認した。初期値は実測値ではない。候補探索の途中結果、履歴集計の上限、完全展開した構成の勝利確率保証は区別する。

### 条件の再帰サイクル

1. 条件全体を確認すると、構成数は表示されるが増加要因を調べられなかった。複数候補を持つ項目の内訳、候補数、その項目を1候補へ固定した場合の構成数を追加した。構成数から計算時間を推定する機能は採用しない。
2. 内訳を追加して再確認すると、値を変えるために元の表へ戻る必要があった。内訳の各値から直接固定できる操作を追加した。初期配置・両チームの能力・数値候補を同じ粒度で扱い、1操作で取り消せる。
3. 一括選択を再確認すると、項目検索中にも非表示項目まで更新していた。表示中の数値項目だけを一括選択するよう変更した。さらに、赤青の差だけを表示し、行単位で反対側の候補に揃えられるようにした。両チーム共通の数値そのものはコピーしない。

### 評価の再帰サイクル

1. 構成一覧を確認し、集計未完了・履歴上限・保証ありの絞り込み、構成ID検索、展開グループ数・保証下限順を追加した。保証未確定を0として並べない。
2. 構成の下の作戦一覧へ粒度を下げ、作戦ID・動作の複数語検索、分類との組合せ、展開数・発見済み最小点差・未決割合の並び替えを追加した。試合展開数はBigIntで比較し精度を保つ。
3. 一行の点差分布が一覧を押し延ばすため、点差範囲を常設し内訳を折り畳んだ。未決の展開がある作戦だけを抽出でき、構造の組数・動作数と代表局面の操作名を追加した。点差順が保証値の順位と誤解されない説明を表示する。
4. 抽出結果を検討資料へ持ち出すため、表示構成と表示作戦のJSON書き出しを追加した。設定、分類版、集計完了状態、履歴上限、終了時刻を含める。フィルターで分布の重みを再計算せず、元の集計を保持する。

### OSSから参照した操作

- [Godot Editor Inspector](https://github.com/godotengine/godot/blob/master/editor/inspector/editor_inspector.cpp): `_property_path_matches` と `_resource_properties_matches` が項目・階層へ検索を適用し、`EditorProperty::get_minimum_size` が復元・ピンなどの行内操作の場所を確保する。条件の探索軸から項目ごとの操作へ掘り下げる構造を参考にした。コードの転用はない。
- [Blender Spreadsheet](https://github.com/blender/blender/blob/main/scripts/startup/bl_ui/space_spreadsheet.py): `SPREADSHEET_HT_header.draw` が選択対象のみの表示とフィルター切替をヘッダーに置き、利用可能性を `_selection_filter_available` で制御する。構成・作戦一覧で対象範囲を明示した絞り込みを採用した。可視性だけを変更し計算結果の意味は変えない。

### 検証

条件履歴と評価抽出の純関数テスト8件を実行し全件成功。対象限定一括編集と取り消し、保証値0と未確定の区別、整数精度を超える展開数の並び、分類・検索・未決の積集合、点差範囲を検証した。型検査成功。ブラウザで確認する操作は、条件の探索軸展開→値固定→取り消し、差分フィルター→行コピー、評価の絞り込み・並び替え・JSON書出し・代表局面への移動。実ブラウザ確認は親タスクで行う。
