# NHK学生ロボコン2027 作戦探索

NHK学生ロボコン2027の作戦検討用。競技ルールはABUロボコン2027と同一と仮定します。用語は手元の日本語参考訳（非公式）に合わせています。

機体能力と数値スペックの組合せから、選べる行動・局面・試合展開を生成するローカルの探索アプリです。固定作戦のカタログ、旧Web計算エンジン、Pythonのマクロ実験は廃止しました。過去の実装と結果はGit履歴に残っています。

## 起動

Python 3.10以上、Node.js 22.12以上が必要です。

```sh
python3 -m pip install -r requirements.txt
cd web
npm ci
npm run build
cd ..
python3 -m explorer
```

[アプリを開く](http://127.0.0.1:4174)。探索は `.explorer-strategy-choices-4/` のSQLiteに自動保存されます。ブラウザを閉じても、Pythonプロセスが動いていれば計算は継続します。プロセスを再起動した場合は「候補を探す」または「全探索を続ける」で保存済みの候補・分岐から再開します。ローカルの127.0.0.1にのみバインドします。

開発時はPythonを起動した状態で `web` 内の `npm run dev` を使います。ViteはAPIを4174番へプロキシします。

## 使い方

1. 赤青の能力候補と、項目別の速い／標準／遅いを選択します。複数選択は独立に組み合わせます。数値は仮定として編集できます。
2. 試合開始・終盤の検証局面、または保存した局面JSONを選びます。動作中のjobを含む局面の初期条件への読み込みは受け付けません。
3. ルール解釈と初期配置を設定し、探索を作成します。
4. 「候補を探す」で10・30・60秒の候補探索を行います。取得個数・混載・受け渡し方法・建設の切替・先行搬送を探索します。相手側も同じ選択肢から探索し、発見した相手手順を候補間で共有して比較します。
5. 候補の「得点と経路」から計算済みの経路を直接開けます。「詳細な全探索」は細かい行動を網羅する検証用です。途中でも局面から行動を選んで分岐を計算できます。
6. グラフのノード・エッジを選び、経路を3Dで再生します。複数の入辺は保持され、別の履歴を選べます。
7. 「評価を計算」で構成・作戦・展開の集計を生成します。別の保存済み探索を比較対象にできます。

グラフは100局面ずつ表示します。範囲外の遷移は詳細の一覧から移動できます。ブラウザ内に全データを一括描画しません。JSONの書出しは調査用で、常用の保存・再開はSQLiteが担当します。

## 探索の意味

位置・経路・初期配置、操作と時間を有限化したモデルです。時刻は1秒単位で記録し、次の動作完了・試合終了まで進めます。操作成功を前提とし、動作中の任意リトライは探索しません。次の動作完了までの待機と、1秒待機を選べます。1秒待機の連続で任意の整数秒の開始遅延を表現します。同じ属性・積み方の物体は個数と属性で選びます。共有在庫は接触時に割り当て、不足する場合は競合結果を分岐します。機体の接触力学、転倒、把持軌道、通信なしで実行できるかは検証しません。未確定のルール解釈は設定に分離しています。

候補探索は、各ロボットの動作完了時に次の行動を独立に選びます。取得個数・混載・床／直接受け渡し・建設途中の切替・先行搬送を固定方針で除外しません。移動は作業地点までの最短経路、待機は次の動作完了と終了直前の反転開始までに限定します。有望な完走経路を進める処理と古い未探索分岐の処理を交互に行い、選ばなかった行動組合せはSQLiteに残します。同じ完全状態の後続は共有し、異なる到達経路はグラフに保持します。

相手への対応検査では、自チーム候補の手順を固定して相手の行動を探索します。相手の手順を他の候補にも適用し、同じ構成の全候補で裁定分岐まで検査済みの共通手順に限って比較点差を表示します。手順が成立しなくなった場合はその局面を記録し、別作戦には置き換えません。表示する候補は経路の代表例であり、全経路一覧・最適性・相手の全対応に対する保証ではありません。

候補と相手の対応を交互に検証し、確認済みの点差を後続候補の探索順へ反映します。途中の候補を保存し、中断・再開できます。候補表の確認済み最小点差は相手全体への保証ではなく、異なる構成の値も検証数と合わせて読む必要があります。

「探索完了」は選択した全構成とモデル内の全分岐の処理完了を意味します。打ち切りを到達不能・0勝と扱いません。180秒より短い終了時刻では、その時点の状態評価であり試合の最終勝敗ではありません。180秒の全構成が実用時間内に完了する保証はありません。

作戦は試合全体の設置・反転・持ち直しの完了順序で分類した群です。分類では移動・リトライと物体IDの違いを除き、種類・個数を使います。詳細な移動と時刻は各試合展開に残ります。分類版と固定切断基準を保存します。分類のIDに解釈上の作戦名を付けません。集計は展開グループを等重み、群内の厳密展開も等重みとし、経路単位の集計を併記します。実大会の勝率ではありません。履歴集計も上限で打ち切る場合は未完了表示になります。

探索完了した構成では、同時行動の混合方針を許した線形計画で赤の勝ち保証を計算します。不確定競合は不利な結果を考慮し、審判判断まで残る同点は下限・上限を分けます。得点差は勝敗保証を維持する保守的下限です。分類群だけに相手の対抗手を限定しません。

## 検証

```sh
python3 -m unittest discover -s tests -v
cd web
npm test
npm run build
```

現在のモデルは `strategy-choices-4` です。旧モデルの保存データ・条件JSONとは互換性がありません。旧 `.explorer/` はそのまま残し、新しい保存先で探索を作り直します。

終了までに完了せず、競技物体にも影響しない移動・リトライは待機にまとめます。物体を返すリトライ、取得、反転は開始時点で資源や得点に影響するため、終了時に動作中となる選択も残します。

修正前に実作戦を組み、相手の反転を入れて再評価した結果は [実利用レビュー](docs/strategy-use-review-2026-10-13.md) を参照してください。待機の削減によるスペック評価の歪みと、全試合作戦の分類上の問題が確認されています。

修正後の自動候補探索と206経路の再検算は [候補探索の実利用結果](docs/discovery-review-2026-10-13.md) を参照してください。`python3 scripts/discovery-benchmark.py` で再現できます。
